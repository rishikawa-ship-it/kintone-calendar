## §1 背景・目的

### 背景

貸出管理アプリ 704（本番）は、カレンダープラグインと Customine（有効 16 ページ）の分業で運用している。分業を維持しにくい部分が出ている。

- DnD は REST PUT 直書きで kintone の保存イベントを通らず、Customine の保存直前・直後処理が走らない。2026-10-19 に Wi-Fi アプリでは DnD を設定で無効化して回避した【事実: メモリ plugin-dnd-enable-setting、REQ_dnd-enable-setting】。
- ポップアップは iframe のため、閉じると保存直後処理が途中で止まる。保存ガードで緩和済みだが構造は変わらない【事実: メモリ customine-page9-incident、plugin-popup-save-guard】。
- 保存直前のブロックは Customine のフィールドエラー経由でしかできない。ページ間の依存が読めず、添字バグ・クエリ記法エラー・重なり判定の誤りで実害が出た【事実: メモリ customine-page9-incident、customine-overlap-condition-bugs】。
- 並列実行による通知落ち、Webhook と取消フローの revision 409 競合、全体失敗（トランザクション）がない【事実: メモリ wifi-weekly-notice-page4-race、automation-plugin-vision】。

### 目的

Customine に任せている処理のうち、ブラウザ実行で成立するものを、プラグインの設定で実現できるようにする。DnD・ポップアップ・標準画面のどの経路でも、同じ整合性チェックと後処理が走る状態にする。これにより DnD の再有効化を可能にする。

### 判断基準（移す／当面 Customine／対象外）

| 基準 | 移す条件 | Customine 継続の条件 |
|---|---|---|
| 経路非依存性 | DnD を含む複数経路で同じ処理が必要 | 特定の画面操作・ボタンからしか起きない |
| ブラウザ実行 | ログインユーザー権限で成立し、画面を閉じても致命的でない | 画面に依存せず動く必要がある（定期・Webhook） |
| 費用対効果 | 移行で不具合の再発源（二重予約・不整合）が減る | 現行が安定し、移行の利得が小さい |

### 2.4 構想との整合【事実: メモリ automation-plugin-vision】

別プラグイン「KC オートメーション」として新設、実行エンジンは `kc-workflow-core.js` で共有。ステップ番号は不変 ID・実行は上から順、前ステップ結果は構造化参照、`bulkRequest` による全体ロールバック、実行ログ、カレンダーからの CustomEvent 契約、取得は常に配列、並び順は独立 UI。ボタン起点以外に人間の入力ステップは置かない。定期実行・スタイル系は Customine 継続。着手時期は「カレンダーのリリース後」（2026-08-25 決定）。カレンダーはリリース済みで、この条件は満たされている【決定 D-4】。**本書はこの構想と矛盾させない。**

## §4 機能要件

### FR-1 実現方式（別プラグイン（汎用）＋アダプタ方式）【決定 D-1】

1. **別プラグイン「KC オートメーション」を新設**する（`KC.Workflow` 解凍拡張案 A は不採用。理由: 構想と整合、設定画面とデプロイ影響が分離、カレンダーなしでも導入可）。
2. オートメーションは **汎用**とし、kintone 標準画面（追加・編集・詳細・一覧）では単独で動く。カレンダーの有無に依存しない。
3. **アダプタ方式**: 保存の入口ごとに「アダプタ」を置き、同じイベント契約（保存前／保存後）に載せる。(a) 標準画面アダプタ＝kintone 標準イベント、(b) カレンダー DnD アダプタ＝CustomEvent（FR-2）、(c) krewSheet 等の外部 UI アダプタ＝同契約に載せる設計とする。krewSheet の公開 JS API に保存前後のフックがあるかは未調査で、別要件とする（U-10）。
4. 実行エンジンは `kc-workflow-core.js` として切り出す（移設元は `KC.Workflow.Core`）。凍結中の `KC.Workflow` は削除せず維持し（0 件なら不活性）、二重実行を避けるため 704 では新方式のルールを `KC.Workflow` 側へ設定しない。

### FR-2 カレンダー側の変更（最小）

1. **保存前フック**: `_commitOptimistic` の重複チェック直後・PUT 前に `kc:before-save` を dispatch する。detail は `{appId, recordId, source:'dnd', op:'update', before:{start,end}, after:{start,end}}` と `waitUntil(promise)`。promise が `{ok:false, message}` を返す、reject する、または上限時間（案: 10 秒）を超えたら **ブロック**（既存の重複チェックの fail-closed と同じ）。ブロック時は既存と同じ巻き戻し＋ `KC.Banner.show`【提案】。
2. **保存後イベント**: PUT 成功後に `kc:after-save` を dispatch（fire-and-forget）。detail は `{appId, recordId, source:'dnd', op:'update', revision, before, after}`【提案】。
3. **失敗の表示**: 保存後処理が失敗したら `kc:after-save-failed` で通知し、カレンダー側が `KC.Banner` に表示。主レコードは PUT 済みのため、巻き戻しは FR-6 の方式に従う。
4. イベント名・ペイロード・発火タイミング（保存前＝PUT 前、保存後＝PUT 成功後）は契約として本書とコメントに固定し、両プラグインで独立してバージョンを上げられるようにする【構想の推奨に従う】。
5. 購読者がいない（オートメーション未導入・未初期化）場合の挙動は、**カレンダーの設定項目**とする【決定 D-1】。選択肢は「そのまま保存する」「保存を止める」。購読者の有無は `waitUntil` の登録有無で判定する【提案】。初期値は U-11。ルールが 0 件のオートメーションは「購読者あり・何もしない」として保存を通す。

### FR-3 設定モデル（1 ルール 1 定義）

1. 1 つの業務ルールは、`phase`（`beforeSave` / `afterSave`）と `routes`（`standard` / `popup` / `dnd`、既定は 3 つとも）を持つ **1 つの定義**とする。経路ごとに複製しない。
2. 各ルールは `enabled`（個別 ON/OFF）、`mode`（`enforce` / `shadow`）、`id`（不変）を持つ。`shadow` は書き込み・ブロックをせず、判定結果だけをログに残す（保存前チェックの並走検証用）【提案】。
3. ステップは番号＝不変 ID、実行順＝上から順。前ステップの結果は構造化参照（プルダウン選択）。番号の振り直しは明示ボタン、参照切れは設定画面で検出【メモリ automation-plugin-vision】。
4. 取得は常に配列（0 件は正常）、更新は 0 件なら何もしない。取得件数は「上限」と「期待（超過でエラー）」を区別。並び順は独立 UI 項目、取得 1 件かつ並び順未指定は警告【同】。
5. 期間の重なりは「`開始 <= 相手の終了 and 終了 >= 相手の開始`」の 1 本の式だけで表す。UI でも `or` 並びを作らせない【メモリ customine-overlap-condition-bugs】。
6. 設定のエクスポート/インポートで AI が書いた JSON を取り込める。部分キーのみも可（NFR-3）。
7. **ルール種別は汎用定義**とする（第 1 段は次の 2 種）【決定 D-3】。判定対象のアプリ・フィールド・集計方法・文言をコードに固定せず、すべて設定で指定する。
   - **集計比較ルール**: 集計対象アプリ、絞り込み条件（条件ツリー）、集計方法（件数／合計／最大など）、比較対象フィールド、演算子、エラー文言、エラー表示先フィールド。
   - **期間重複ルール**: キーとなるフィールド（複数可）、開始/終了フィールド、対象ステータス条件、自レコード除外。
   - 日付制限ルール（前営業日編集禁止の汎用化）は第 1 段に含めない。U-6 の確認後に追加判断する。

### FR-4 保存前チェックの経路（C1 相当）

| 経路 | 実現方法 |
|---|---|
| 標準画面（追加/編集） | `app.record.create.submit` / `app.record.edit.submit` を購読し、違反はフィールドエラーまたは `event.error` で止める |
| ポップアップ | iframe 内も同じ `desktop.js` が読み込まれる（§2.3）ため、標準画面と同一のイベントで拾える。**止め方は input-error（フィールドエラー）を必ず含める**。保存ガードが失敗検知に使うのは notifier と input-error で、Customine のブロックは input-error のみのため【メモリ plugin-popup-save-guard】 |
| DnD | FR-2-1 のフック |

- 台数チェックは固有機能にしない。FR-3-7 の集計比較ルールの 1 設定例（「同期間の他申請の台数合計 ＋ 自申請の台数 > 在庫」でブロック、`=` は許可【メモリ session-2026-09-04: E3】）として付録 A に記す。
- 在庫の算出元と「貸出予定のみ」等の条件は、Customine 定義の写経ではなく §9 U-1 で確定してから設定値にする。
- チェックのクエリが失敗したら、DnD と同じく **ブロックして再操作を促す**（fail-closed）【既存方針: desktop.js:2754】。

### FR-5 保存後処理の経路（C2/C4/C7 相当）

| 経路 | 契機 |
|---|---|
| 標準画面・ポップアップ | iframe/標準画面の `app.record.*.submit.success`。**親ウィンドウ側の `notifyRecordSave` 検知（`2260/2343`）は新方式では発火させない**（二重発火防止。既存の `data-kc-modal` マーカーで判定） |
| DnD | `kc:after-save` を購読 |

- 保存後処理は「ステータス・台数・開始・終了が変わったとき」「貸出予定のみ」など、発火条件をツリーで設定できる（既存の `conditionTree` を共有コアへ）。
- 行の追加・削除済化・期間の取り直し・連結文字列更新・台帳 653 の更新・通知レコード追加を、可能な限り 1 回の `bulkRequest` にまとめる（FR-6）。
- ルックアップのコピー先は、REST で参照先キーを書くと取り直される挙動を前提に設計する。不一致値はエラーでレコード不作成、空値は素通り、絞込条件は REST でも適用される【メモリ customine-page9-incident】。**空・不正なキーは書き込み前に検証して中断**する（空ルックアップ行を作らない）。
- 標準画面・ポップアップでは、`submit.success` のハンドラが Promise を返せば kintone が遷移を待つ可能性がある【推測。cybozu.dev で要裏取り（U-4）】。成立するなら iframe 即時クローズによる中断問題が構造的に解消する。成立しない場合は保存ガード（既存）に依存する。

### FR-6 トランザクションと実行ログ

- 保存後処理の kintone 書き込みは 1 つの `bulkRequest` で送り、1 件でも失敗したら全件ロールバックされる。公式仕様: 1 回 **最大 20 リクエスト**、失敗時は後続を実行せず全取消、対象 8 API（レコード登録/更新/削除、ステータス更新等）【事実: cybozu.dev 一括リクエストの仕様を 2026-10-19 に確認】。
- 件数は「リクエスト数」で数える。複数レコード登録/更新（最大 100 件）を使えば、台数が増えても 20 を超えにくい。超える見込みなら設定画面で警告し、実行時は分割せずエラー終了する【提案】。
- **DnD は、主レコードの更新と後処理を 1 つの `bulkRequest` で一括し、失敗すれば全部なかったことにする**【決定 D-5】（保存前フェーズでオートメーションが追加リクエストを `detail.addRequest()` で渡し、カレンダーが主 PUT と合わせて送る【提案】）。実現性は U-5 で検証する。
- **標準画面・ポップアップの保存後は巻き戻しなし**【決定 D-5】。kintone 標準の保存が先に確定するため、後処理だけが一括になる。失敗時はバナー＋実行ログ＋「再実行」導線とする。
- 実行ログに、ルール ID・ステップ番号・入力・件数・投げたクエリ・結果・経過時間・ユーザーを残す。保存先は U-7。

### FR-7 二重動作の防止と切替

1. 移行はルール単位。手順: ①`shadow` で並走し Customine の結果と照合 → ②Customine の該当ページを無効化（複製→旧ページを「【アーカイブ】…」にして無効、「kintoneアプリへ登録」まで反映されない【メモリ customine-editor-operations】）→ ③プラグインのルールを `enforce` → ④不具合時は逆手順で戻す。
2. ②と③は同じ作業枠で連続して行う。並走すると行が二重に増えるため、**保存後ルールの `shadow` は書き込みをしない**。
3. DnD の再有効化（`dndEnabled`）は、第 2 段のゲート（§7）を満たしてから Wi-Fi アプリで ON に戻す【決定 D-2】。コードの既定は変えない。
4. 本番アプリへのルール反映（`enforce` 化・Customine 無効化を含む）は、該当段のテスト合格後にのみ行う【決定 D-4】。

## §8 既知の制約

- ブラウザ実行の限界: ログインユーザー権限でしか動かない（閲覧・書き込み権限のないアプリ/レコードは触れない）、画面を閉じたら止まる、定期実行はできない【メモリ automation-plugin-vision】。
- ポップアップは iframe。閉じると JS が即死する。保存ガード（保存中は閉じない・90 秒上限）で緩和しているが、**90 秒を超える処理や iframe 外のタブ閉じは防げない**【メモリ plugin-popup-save-guard】。
- 二重発火防止: iframe 内で動く購読は自分が iframe かどうかを `window.frameElement.dataset.kcModal` で判定する（既存）。新方式では「record ページ自身が発火元」を原則とし、親側の検知は新方式では使わない。
- Webhook（C5）と並走する: DnD の REST 更新でも Webhook は起動する（サーバー側のため）。Webhook が申請レコードを更新すると revision が進むため、後処理で申請レコードを PUT する場合は revision を指定しない、または直前に再取得する【推測。U-5 で検証】。
- 保存前ブロックでも申請番号は消費される（欠番許容の決定済み）。
- `bulkRequest` は 20 リクエスト上限・同一スペース内のアプリのみ。ルックアップは「不一致でレコード不作成／空は素通り／画面と API で絞込の扱いが違う」。
- 設定の変更は、開いているカレンダーのリロードまで反映されない。
