**文書番号**: REQ_workflow-actions

**作成者**: designer（サブエージェント）
**ステータス**: 設計完了（未実装・ユーザー確認待ち事項あり）
**入力資料**: 管理者からの委譲プロンプト（ユーザーヒアリング確定事項を含む）
**対象ファイル（実装時）**:
- `plugin/src/js/desktop.js`（カレンダー本体。トリガーフック・ワークフロー実行エンジン）
- `plugin/src/js/config.js`（設定画面ロジック。config version 13 へ）
- `plugin/src/html/config.html`（設定画面。セクション6「ワークフロー」新設 + 詳細編集モーダル新設）
- `plugin/src/css/config.css`（新規 UI のスタイル）

**方針（ユーザーヒアリングで確定・変更禁止）**:
- フローUI: **ステップ列挙型**（分岐なしの直列フロー）。既存のテーブルUIパターン（行追加/削除/DnD並び替え）を踏襲する。
- 実行権限: **ログインユーザー権限**（`kintone.api` をそのまま使用。API トークン認証は対象外）。
- トリガーは **3種**: (1) カレンダー: 作成・更新、(2) カレンダー: 削除、(3) kintone 編集画面: 保存。
- 更新先レコード特定は **キー一致検索**（upsert オプションを含む）。
- 発火条件はユーザーが定義可能（フィールド選択→値選択の UI）。
- **REST API 経由の外部更新はトリガー対象外**（プラグイン＝ブラウザ JS では検知不可のため）。
- **分岐・並列フロー、Webhook 発信、メール送信等のアクション種別拡張は将来拡張とし今回スコープ外**。

## 1. 背景・目的

kintone-calendar プラグインで管理する予定（レコード）の作成・更新・削除を起点に、**別の kintone アプリへレコードの追加・更新を行いたい**という要望がある。

`kintone-rules.md` の実装方針優先順位（Customine 最優先）に照らすと、まず Customine の利用可否を検討すべきだが、本要望は次の理由により **Customine を経由せずプラグイン内で完結させる** ことが確定事項としてヒアリング済みである。

- カレンダー独自の3種類のトリガー（DnD/リサイズ、モーダル経由の保存、kintone 標準編集画面の保存）を一元的に捕捉する必要があり、これらは既に `desktop.js` 内に実装済みのイベント処理・DOM 監視ロジックと密結合している（§2 参照）。Customine 側から見ると DnD 操作はカスタマイズ JS 内で完結する UI 操作であり、Customine のイベントフックの対象にならない。
- プラグインの設定情報（フィールドマッピング・重複チェック設定等）と同じ config ストア (`kintone.plugin.app.setConfig`) に、ワークフロー定義も一元管理したいという運用上の要望（設定の一箇所集約）。
- `PLUGIN_DISCUSSION.md` で示されている通り、本プラグインは「非エンジニアへの設定委譲」を目指す方向で設計されており、ワークフロー設定も同一の GUI 上で完結させることが既定路線と整合する。

本書は、この「ワークフロー」機能の要件定義（トリガー・条件・アクションの構成、config データ形式、既存コードへの差し込み点、UI 配置）を確定するために作成する。実装（コード変更）は行わない。

## 2. 現状分析

### 2.1 カレンダー側の3つの保存・削除経路（裏取り済み）

ユーザーヒアリングでは「新規作成モーダル、DnD/リサイズ、編集モーダル経由の保存」がまとめて1つのトリガー種別（トリガー1）とされているが、実装を裏取りした結果、**これらは技術的には2つの異なる検知メカニズムに分かれる**ことが判明した。加えて、削除・kintone標準編集画面の保存についても既存コードとの整合性を確認した。

#### 2.1.1 DnD（移動・リサイズ）

- 実体: `KC.DnD` 内 `_commitOptimistic()`（`desktop.js:2264-2385`）。
- 重複チェック（有効時）を通過した後、`KC.Api.updateEvent(payload)`（`desktop.js:2370`、PUT `/k/v1/record.json`、楽観ロック `revision` 付き。`updateEvent` 本体は `desktop.js:1391-1428`）を呼ぶ。
- **フック候補**: `updateEvent(payload).then(function (resp) { ... })`（`desktop.js:2371-2378`）の成功コールバック内。ここは PUT が **サーバー側で成功したことが確定した後** の地点であり、`payload`（更新後の start/end 等）と `origEv`（更新前の KcEvent）の両方にアクセスできる。
- 送信は非同期・非ブロッキング（`.then/.catch`、`await` していない。`desktop.js:2366`のコメント「API を非同期送信（楽観的: レスポンスを待たない）」）。ワークフロー実行もこの非同期性を踏襲すべき（§3.6 NFR-2）。
- **注意**: `KcEvent`（`_recordToEvent()`, `desktop.js:804-903`）が保持するフィールドは、タイトル/開始/終了/終日/色/場所/メール/アカウント/メモ/ステータスと、権限・フィルタ設定で指定されたフィールドの値（`permissionFields` / `valueFields`）のみ。ワークフローのフィールドマッピングで **任意のフィールド** を参照したい場合、`KcEvent` に値が無い可能性が高く、`KC.Api.getRecord(ev.id)`（`desktop.js:1447-1453`）による再取得が必要になるケースがある（§3.4.3 参照）。

#### 2.1.2 新規作成モーダル・編集モーダル経由の保存

- `KC.Popup.openCreate()`（`desktop.js:2024-2052`）/ `openEdit()`（`desktop.js:2059-2082`）は、kintone 標準の編集・詳細画面（`/k/{appId}/edit` または `/k/{appId}/show#record=N`）を **同一 DOM 内 iframe** で開く（`window.open` ではない。コメント `desktop.js:1461-1467`）。
- iframe は `sandbox="allow-same-origin allow-scripts allow-forms allow-popups allow-modals allow-downloads"`（`desktop.js:1810-1813`）で、同一オリジン（cybozu.com）のため `iframe.contentDocument` に親からアクセス可能。
- 保存検知は kintone の `kintone.events` を使わず、**親ウィンドウ側で完結する独自メカニズム**で行っている:
  1. iframe 内の「保存」ボタンをテキスト一致で検出し、クリックで `KC.Popup._savePending = true` をセット（`_attachSaveHandler()`, `desktop.js:1585-1627`）。
  2. iframe の URL が保存成功パターン（`/k/{appId}/show#record=N` かつ `mode=edit` を含まない）に遷移したことを、`load` イベント（`desktop.js:1818-1876`）と `hashchange` / 1500ms ポーリング（`_checkIframeUrl()`, `desktop.js:1901-1960`）の両方で検知する（`_isSaveSuccessUrl()`, `desktop.js:1644-1654`）。
  3. `_savePending && _isSaveSuccessUrl(loc)` が真になった時点（`desktop.js:1843-1855` および `:1911-1923`）で `_savePending` をリセットし、`KC.Render._refreshImmediate()` → `KC.Popup._close()` を呼ぶ。バリデーションエラー時は URL 遷移が起きないため、この分岐は通らない（コメント `desktop.js:1576-1578`）＝ **この分岐は必ず「保存成功後」**。
- **フック候補**: 上記 `desktop.js:1843-1855` と `:1911-1923`（load ハンドラ／ポーリングの2箇所、ロジックはほぼ重複しているため両方に同じフック呼び出しを追加する必要がある）。ここでは **レコード ID のみ**（URL の `record=N`）が分かり、フィールド値は分からない。ワークフロー実行のためには `KC.Api.getRecord(recordId)` での再取得が必須。
- 新規作成か編集保存かの区別: `openCreate` は `record=` パラメータなしで `/edit` を開始し、`openEdit` は `record=N` 付きで開始する。`KC.Popup` に現在「作成中か編集中か」を示すモード変数は存在しない（`_show(url)` は URL 文字列のみを受け取る）。ワークフローの「作成 / 更新」判定に必要なら、`_show()` 呼び出し元（`openCreate`/`openEdit`）で `KC.Popup._mode = 'create' | 'edit'` のような状態を追加保持する実装が必要（新規、既存コードに無い）。

#### 2.1.3 kintone 標準編集画面の保存（カレンダーを介さない）

- `kintone.events.on(['app.record.create.submit.success', 'app.record.edit.submit.success'], ...)`（`desktop.js:10832-10843`）が既に存在する。ただし現在の実装は `if (window.opener) { ... }` を分岐条件にしており、これは **旧アーキテクチャ（`window.open` によるポップアップ）を前提としたコード**（コメント `desktop.js:1463-1465` に明記の「旧実装: window.open による別ウィンドウポップアップ」に対応）。
- 現行の iframe オーバーレイモーダル方式では `window.opener` は常に `null`（iframe は `window.open` で開いていないため）。したがって **このハンドラのイベント自体は発火するが、`if (window.opener)` の中身は現状決して実行されない（事実上の死んだ分岐）**。
- 一方、`manifest.json`（`plugin/manifest.json:14-17`）は `desktop.js` をアプリの `desktop` カスタマイズとして登録しており、ビュー単位のスコープ指定はない。このため **同一の `desktop.js` が、カレンダービューだけでなく、このアプリの標準一覧・詳細・作成・編集画面（＝カレンダーの iframe モーダルが読み込む `/edit`・`/show` も含む）すべてに読み込まれる**。
- 結論: `app.record.create.submit.success` / `app.record.edit.submit.success` は、(a) カレンダーの iframe モーダル内で保存した場合と、(b) このアプリの通常の一覧・詳細画面から直接保存した場合の **両方で発火する**。(a) と (b) を区別せずにこのハンドラでワークフローを実行すると、カレンダー経由の保存が「トリガー1」と「トリガー3」の両方としてカウントされてしまう（§2.3・§3.5 NFR-1 参照）。

#### 2.1.4 削除

- `kintone.events.on('app.record.detail.delete.submit', ...)`（`desktop.js:10848-10855`）が既に存在し、同様に `if (window.opener)` ゲートのため現状は事実上死んだ分岐。
- `KC.Api.deleteEvent()`（`desktop.js:1431-1438`、DELETE `/k/v1/records.json`）は定義されているが、**呼び出し箇所がコードベース全体を検索しても存在しない（未使用/デッドコード）**。カレンダー UI 上に削除ボタン・削除操作の実装は見当たらず、削除は常にモーダル内の kintone 標準詳細画面（またはアプリの標準詳細画面）が持つ「削除」ボタン経由で行われている、と推定される。
- `KC.Popup` には保存ボタン検知（`_attachSaveHandler`）・キャンセルボタン検知（`_attachCancelHandler`）に相当する **削除ボタン検知の仕組みは存在しない**。削除後の画面遷移（一覧へのリダイレクト）は `_isAllowedUrl()`（`desktop.js:1674-1691`）の対象外 URL に該当するため、現状は「許可外 URL 遷移」として汎用的に `_close()` されるだけであり、「削除が成功したこと」を明示的に検知するロジックはない。
- `app.record.detail.delete.submit` は kintone JS API 上、削除確認ダイアログで「削除する」を押した際に発火する **削除実行前のキャンセル可能イベント**（`event.record` に削除対象レコードの全フィールド値が含まれる）である。`.submit.success` に相当する「削除確定後」イベントは、少なくとも本コードベースの既存実装ではハンドリングされていない（kintone 公式仕様上そのようなイベントが存在するか自体、本書では未確認。§7.1 U-3 参照）。

### 2.2 KC.Banner（既存の通知バナー）

- `KC.Banner`（`desktop.js:6968-7043`付近）は `.kc-root` 直下にシングルトンで挿入されるエラーバナー。`show(message, opts)` / `hide()` のみを持ち、**同時に表示できるメッセージは1件のみ**（`show()` 内、既存バナーがあればテキストを上書きするだけ。`desktop.js:6980-6986`）。
- 既存用途: DnD 重複チェック失敗時のブロック通知（`desktop.js:2313, 2318, 2336, 2343, 2345` 等）。
- ワークフロー失敗通知に流用する場合、DnD 重複チェックのバナーと表示が競合（後勝ちで上書き）する可能性がある（§7.2 R-2）。

### 2.3 対象アプリへのクロスアプリ REST 呼び出しの前例

- `KC.Api.checkOverlapQueryModeB()`（`desktop.js:1233-1388`、DnD重複チェック モードB）が、既に **自アプリ以外のアプリ（関連先アプリ）** へ `kintone.api(url, 'GET', { app: relatedAppId, ... })` を発行している（`desktop.js:1327-1332`）。
- 同関数は権限エラーを `err.code === 'CB_AU01' || err.status === 403` で判定し、`isPermissionError` フラグとして呼び出し元に返す実装（`desktop.js:1335-1337`）。この判定パターンはワークフローのエラーハンドリングでも流用できる（正確なエラーコード体系は §7.1 U-1 で確認事項として扱う）。
- `KC.Config.detectFields()`（`desktop.js:94-140`）・config.js の `loadFields()`（`config.js:2914-2919`）はいずれも自アプリの `app: KC.Config.getAppId()` / `app: getAppIdFromUrl()` で `/k/v1/app/form/fields.json` を呼んでいるが、**この API は `app` パラメータに任意のアプリ ID を指定すれば、そのアプリの閲覧権限を持つユーザーであれば取得可能**（kintone REST API 仕様上の一般則。本コードベースでは他アプリ ID を渡す実装はまだ存在しないため、これは新規実装が必要な箇所）。

### 2.4 config.js の設定保存形式（version 12 が現行 — 委譲時の前提と差異あり）

委譲プロンプトでは「config version 11」を前提としていたが、直近コミット `71d7d2a`（モードB filterCond 連動修正）で **既に version 12 に上がっている**ことをコード上で確認した（`config.js:3-23` のヘッダーコメント、`config.js:166`, `config.js:2745`, `config.js:2867`, `config.js:3526`）。本書ではこの事実を前提に、新機能導入時のバージョンを **version 13** として設計する。

- `currentConfig` のトップレベル構造（`config.js:160-191`）: `version, fieldMapping, permissionRules, fieldValueRules, searchTargets, defaultPermission, filterConfig, views`。
- `loadInitialConfig()`（`config.js:2724-2884`）が `version` を段階的に判定し、v2→v5→v6→v7→v8→v9→v10→v11→v12 の順で1段階ずつマイグレーションを適用する連鎖処理になっている（各 `if (Number(parsed.version) < N)` ブロック、`config.js:2764-2851`）。新規追加時も **この連鎖に1段追加するだけ**（既存マイグレーションを変更しない）で済む設計になっている。
- `saveConfig()`（`config.js:3376-3564`）内 `finalConfig`（`config.js:3525-3536`）が実際に `kintone.plugin.app.setConfig()` へ渡す最終オブジェクト。ここに新キーを追加する必要がある。

### 2.5 既存 UI パターン（新規 UI 設計の再利用対象）

- **行リスト（テーブル型・DnD 並び替え・追加/削除）パターン**: 権限フィールド設定（`buildFieldValueRow()`, `config.js:1434-1476`）・権限ユーザー設定（`buildPermissionRow()`, `config.js:1182`）・フィルタ設定（`buildFilterGroupRow()`, `config.js:2047`）が共通して採用。行ドラッグは `attachRowDragEvents(row, handle)`（`config.js:1087`）で共通化されており、`row.parentNode` を基準に `insertBefore` する実装のため、コンテナがどのセクションに置かれても機能する（`REQ_config-reorg.md §2.3` で確認済みの事実と同じ）。
- **「フィールド選択→値選択」連動パターン**: `buildFieldValueFieldSelect()`（`config.js:1508-1548`）でフィールド一覧セレクトを構築し、`buildFieldValueValueSelect()`（`config.js:1556-1573`）が `fieldSel` の `change` イベントで `rebuildValueSelect()` を呼び、選択フィールドの型に応じて値の選択肢（DROP_DOWN/RADIO_BUTTON の選択肢一覧、CHECK_BOX の複数選択等）を動的に再構築している。これはユーザーヒアリングで要望されている「発火条件（フィールド選択→値選択）」の実現方式として直接流用できる。
- **モーダルダイアログパターン**: `#kc-copy-modal`（`.kc-modal-overlay`、`config.html:509-527`、「ほかビューからの設定コピー」用）が既に存在する。設定画面全体はこの1箇所を除き単一ページのフラット構成（`REQ_config-reorg.md` で確認済みの5セクション構成、見出し行 `config.html:34, 147, 204, 316, 393`）だが、モーダル自体の実装パターンは既にあるため、ワークフローの「詳細編集」に転用可能（§3.7 参照）。

## 3. 要件

### 3.1 トリガー種別（FR-1）

| トリガー ID | 名称 | 発火元（実装フック） | 発火条件判定に使う値 |
|---|---|---|---|
| `calendarSave` | カレンダー: 作成・更新 | (a) DnD/リサイズ: `_commitOptimistic()` 内 `updateEvent().then()` 成功時（`desktop.js:2371-2378`）<br>(b) モーダル経由の保存: `KC.Popup` の保存成功検知（`desktop.js:1843-1855`, `:1911-1923`） | (a) は `KcEvent` 保持フィールド＋必要に応じ `getRecord()` 再取得<br>(b) は `getRecord(recordId)` で全フィールド取得（必須。§2.1.2） |
| `calendarDelete` | カレンダー: 削除 | `app.record.detail.delete.submit`（既存ハンドラ `desktop.js:10848-10855` を拡張。`window.opener` ゲートを撤去し新ロジックに置換） | `event.record`（イベント発火時点で削除対象レコードの全フィールド値を含む。削除確定前のスナップショットとして利用） |
| `kintoneEditSave` | kintone 編集画面: 保存 | `app.record.create.submit.success` / `app.record.edit.submit.success`（既存ハンドラ `desktop.js:10832-10843` を拡張） | `event.record`（保存後の全フィールド値を含む） |

**設計判断（重要）**: `kintoneEditSave` は「カレンダーを介さない、このアプリの標準編集画面での保存」に限定する。実装上、`desktop.js` は iframe 内にも読み込まれるため（§2.1.3）、**このハンドラが「カレンダー自身のモーダル iframe の中」で発火した場合は `kintoneEditSave` の対象外とし、何もしない**（トリガー1側 `calendarSave` の (b) が既にカバーするため、二重発火防止。§3.5 NFR-1 参照）。

判定方法（提案）: `KC.Popup._show()`（`desktop.js:1771`）で iframe 要素に識別用マーカーを付与する（例: `iframe.dataset.kcModal = '1'`）。iframe 内で実行される `desktop.js` の当該イベントハンドラは、`window.self !== window.top && window.frameElement && window.frameElement.dataset.kcModal === '1'` を満たす場合に「自分はカレンダーの iframe モーダルの中にいる」と判定し、`kintoneEditSave` の発火をスキップする。

### 3.2 ワークフロー定義の構成（FR-2）

ステップ列挙型・直列フローとして、1ワークフローを以下の階層で構成する。

```
ワークフロー
  ├─ 基本情報: 名前、有効/無効
  ├─ トリガー: トリガー種別（§3.1 の3種から1つ）
  ├─ 発火条件: 0件以上（AND結合。フィールド選択→値選択の行リスト）
  └─ アクション: 1件以上（上から順に実行するステップ列挙）
        ├─ 対象アプリ（アプリID）
        ├─ 動作モード: 新規作成のみ / 更新のみ / upsert（キー一致で検索し、あれば更新・なければ新規作成）
        ├─ キー一致設定（更新のみ・upsert 時に必須）: 自アプリのフィールド ⇔ 対象アプリのフィールド
        ├─ 複数件ヒット時の扱い: 更新をブロックしエラー扱い（既定・固定。§3.4.4）
        ├─ フィールドマッピング: 対象アプリの各フィールドに対し「自アプリのフィールド値」または「固定値」を割り当て
        └─ このアクションが失敗した場合、後続アクションを実行するか（既定値の提案は §3.4.6。要ユーザー確認）
```

1つのトリガー種別に対して複数のワークフローを定義できる（例: `calendarSave` に対して2つの独立したワークフローを設定可能）。ワークフロー間の実行順序は「ワークフロー一覧」内の並び順（DnD 並び替え）に従う。

### 3.3 発火条件（FR-3）

- 0件（無条件で常に実行）〜複数件（AND結合のみ。OR結合は将来拡張）。
- UI は §2.5 の「フィールド選択→値選択」パターン（`buildFieldValueFieldSelect`/`buildFieldValueValueSelect`, `config.js:1508-1573`）を流用する。
- 対象フィールドの型は、既存の権限フィールド設定と同様に DROP_DOWN / RADIO_BUTTON / CHECK_BOX / STATUS を基本としつつ、ワークフローでは加えて **SINGLE_LINE_TEXT 等の文字列系フィールドとの完全一致条件** も必要になる可能性が高い（例:「特定の申請番号の時だけ実行」）。対象フィールド型の最終確定は §7.1 U-2 で確認する。
- 判定に使う値の取得元は、トリガー種別ごとに §3.1 の表の「発火条件判定に使う値」列に従う（`calendarSave` の DnD 経路のみ、KcEvent に値が無い場合は追加 GET が必要になる点に注意。§2.1.1）。

### 3.4 アクション（FR-4）

#### 3.4.1 対象アプリ・フィールド取得

- 設定画面でアプリ ID を入力すると、`/k/v1/app/form/fields.json`（`app: <入力されたID>`）を呼び出しフィールド一覧を取得する（§2.3 で確認した通り、他アプリ ID を渡しても閲覧権限があれば取得可能）。
- 取得失敗時（アプリが存在しない／権限がない）はエラーメッセージを表示し、フィールドマッピング UI を無効化する。

#### 3.4.2 動作モード

| モード | 挙動 |
|---|---|
| 新規作成のみ | 常に `POST /k/v1/record.json`（`app: targetAppId`）でレコードを追加する |
| 更新のみ | キー一致検索でヒットしたレコードのみ `PUT /k/v1/record.json` で更新する。ヒットしない場合は「何もしない」（エラー扱いにはしない） |
| upsert | キー一致検索を行い、ヒットすれば更新、ヒットしなければ新規作成する |

#### 3.4.3 フィールドマッピング

- 対象アプリの各フィールドに対し、(a) 自アプリのフィールド値をそのまま渡す、(b) 固定値を設定する、のいずれかを選択できる。
- 型不一致の扱い（提案。§7.1 U-4 で最終確認）:
  - DATETIME → DATE: 日付部分のみを渡す（`createEvent`/`updateEvent` の DATE 変換ロジック `desktop.js:1082-1090, 1396-1404` と同様、時刻を切り捨てる）。
  - DATE → DATETIME: 00:00:00 を補完して渡す。
  - USER_SELECT → SINGLE_LINE_TEXT 等: ユーザー名（`name`）またはコード（`code`）のどちらを渡すか設定可能にする（既定はコード）。
  - CHECK_BOX（複数選択）→ 単一値系フィールド: 非対応（設定画面でこの組み合わせの選択自体を禁止する）。
  - それ以外の未対応の組み合わせは、設定保存時のバリデーションでブロックし、エラーメッセージを表示する。
- DnD トリガー（`calendarSave` の (a)）でマッピング元フィールドが `KcEvent` に保持されていない場合、ワークフロー実行時に `KC.Api.getRecord(ev.id)` で該当レコードを再取得してから mapping を評価する（§2.1.1）。

#### 3.4.4 キー重複・複数ヒット時の挙動

- キー一致検索で対象アプリ側に **2件以上ヒットした場合は、更新を行わずエラー扱い**とする（安全側デフォルト。どのレコードを更新すべきか自動判断しない）。
- バナー通知例:「ワークフロー『{name}』: キー『{自アプリフィールド}={値}』に一致するレコードが対象アプリ側に複数件見つかったため、更新をスキップしました。」

#### 3.4.5 実行順序

- アクションは配列順に**逐次実行**する（並列実行はしない。前段の結果を後段が使うケースを将来的に許容するため）。

#### 3.4.6 失敗時の継続/中断（要ユーザー確認）

- 提案: 既定値は「継続」（`continueOnError: true`）。ベストエフォート方針（§3.6 NFR-3）と整合させ、1つのアクションの失敗が後続アクション・カレンダー本体の保存を止めないことを既定とする。
- アクションごとに「失敗時に後続を中断する」チェックボックスで上書き可能にする（既定 OFF＝継続）。
- **この既定値（継続 vs 中断）はヒアリング未確定。§7.1 U-5 で確認する。**

### 3.5 二重発火防止（NFR-1）

- `calendarSave` と `kintoneEditSave` は、同一の保存操作に対して片方のみが発火するよう、§3.1 の iframe マーカー判定で排他制御する。
- `calendarSave` 内部（DnD 経路 と モーダル経路）は、それぞれ独立した操作（DnD操作 or モーダルでの保存操作）に対応するため、同一操作が両方から二重発火することは構造上ない。
- モーダル経由の保存検知（`_isSaveSuccessUrl` 判定、`desktop.js:1843-1855` の load ハンドラと `:1911-1923` のポーリング/hashchange ハンドラ）は、`_savePending` フラグを検知直後にリセットする実装（`desktop.js:1845, 1913`）のため、単一実行環境（JS シングルスレッド）において2つの検知経路が同一の保存を二重処理することはない（既存コードで担保済み。ワークフロー呼び出しをこのブロックの中に追加するだけでよい）。
- ワークフロー間の多重実行（同一トリガーに複数ワークフローを設定した場合の意図した複数実行）は二重発火とは区別する（仕様通りの動作）。
- **スコープ外の残存リスク**: 複数アプリにまたがるワークフローの循環（例: A アプリのワークフローが B アプリを更新し、B アプリ側にも本プラグインが導入されていて B → A へ書き戻すワークフローが設定されている場合の無限ループ）は、本プラグインが単一アプリの config のみを管理する設計上、**技術的な自動検知はスコープ外**とし、運用上の注意事項として明記する（§7.2 R-1）。

### 3.6 実行方式・パフォーマンス（NFR-2）

- ワークフロー実行は**非同期・fire-and-forget**とする。カレンダー本体の保存・削除・モーダルクローズ・再描画を待たせない。
  - DnD: `updateEvent(payload).then(function (resp) { ...; KC.Workflow.run(...).catch(...); })` のように、既存の非ブロッキング `.then` チェーンの中で呼び出す（`await` しない）。
  - モーダル保存検知: `KC.Render._refreshImmediate()` / `KC.Popup._close()` の呼び出し（`desktop.js:1850-1853`, `:1918-1921`）をブロックしない位置で `KC.Api.getRecord()` → ワークフロー実行を非同期に開始する。
  - `kintoneEditSave` / `calendarDelete`: kintone イベントハンドラは `return event` を同期的に即座に行い、ワークフロー実行はその前後で `await` せず非同期に開始する（`kintone-rules.md` の「event は必ず return する」を遵守しつつ、ワークフロー完了を待たない）。
- 複数アクションは逐次実行だが、各アクションの REST 呼び出し自体は非同期（Promise chain）。UI 側のローディング表示・ブロッキングは行わない。

### 3.7 エラーハンドリング・通知（NFR-3）

- 方針: **ベストエフォート**。カレンダー側の操作（作成・更新・削除）自体は、ワークフローの成否に関わらず既に完了しているため、ロールバックはしない。
- 失敗時（権限不足・対象アプリ削除・キー重複複数ヒット・ネットワークエラー等）は、`KC.Banner`（`desktop.js:6968-7043`）を用いてカレンダー画面上部に通知する。
  - 既存の DnD 重複チェックバナーと同時に表示され得る点は制約として残る（§7.2 R-2 で対応方針を確認）。
  - 権限エラー判定は `checkOverlapQueryModeB()` の前例（`err.code === 'CB_AU01' || err.status === 403`, `desktop.js:1335-1337`）を踏襲するが、対象アプリへの「レコード追加・更新権限不足」で実際に返るエラーコードは異なる可能性がある（§7.1 U-1）。
  - `console.error` にも詳細（ワークフロー名・アクション・対象アプリID・エラー内容）を出力する。
- 成功時は特に通知しない（サイレント成功。ログのみ `console.log`／`_log`）。

### 3.8 削除トリガーのスナップショット（NFR-4）

- `app.record.detail.delete.submit` は削除実行前に発火し `event.record` に削除対象レコードの全フィールド値を含む（§2.1.4）。この `event.record` をそのままワークフローの発火条件判定・フィールドマッピングのソースとして使用する。
- 追加の GET は不要（削除後は当該レコードが存在しなくなるため GET できない。イベント時点のスナップショットを使うことが必須）。
- **リスク**: このイベントは「削除確定前」に発火するため、何らかの理由でこの後の実際の DELETE 処理自体が失敗した場合（サーバー側エラー・権限不足等）でも、ワークフロー側は既に実行されてしまう可能性がある（§7.2 R-3）。

## 4. 受入基準

Given/When/Then 形式で記述する。

### AC-1: カレンダー経由の作成・更新（モーダル）がワークフローの `calendarSave` トリガーを発火する

- **Given** `calendarSave` トリガーのワークフローが1件、条件なしで有効化されている
- **When** 管理者がカレンダーの新規作成モーダルで予定を作成し保存する
- **Then** 保存成功検知（`_isSaveSuccessUrl` 判定）の直後に、当該ワークフローのアクションが実行される
- **And** カレンダーのモーダルクローズ・再描画はワークフローの完了を待たずに行われる

### AC-2: DnD（移動・リサイズ）が `calendarSave` トリガーを発火する

- **Given** `calendarSave` トリガーのワークフローが1件、有効化されている
- **When** 管理者がカレンダー上で予定をドラッグ&ドロップして移動し、重複チェック（有効時）を通過して PUT が成功する
- **Then** PUT 成功コールバック内でワークフローのアクションが実行される
- **And** DnD 操作自体の UI 応答（ゴースト解除・再描画）はワークフロー完了を待たない

### AC-3: kintone 標準編集画面からの直接保存が `kintoneEditSave` トリガーを発火し、カレンダーモーダル経由の保存では発火しない

- **Given** `kintoneEditSave` トリガーのワークフローが1件、有効化されている
- **When** (a) このアプリの通常の一覧画面から直接レコードを編集・保存する
- **Then** (a) の場合はワークフローが実行される
- **When** (b) カレンダーの編集モーダル（iframe）経由でレコードを保存する
- **Then** (b) の場合は `kintoneEditSave` トリガーのワークフローは実行されない（`calendarSave` 側のみ実行される）

### AC-4: 削除トリガーが削除前のフィールド値でワークフローを実行する

- **Given** `calendarDelete` トリガーのワークフローが1件、削除対象レコードのあるフィールド値を条件に指定して有効化されている
- **When** 管理者がカレンダーのモーダル内、または標準画面からレコードを削除する
- **Then** `app.record.detail.delete.submit` イベントの `event.record` を用いて条件判定・フィールドマッピングが行われ、対象アプリへのアクションが実行される

### AC-5: upsert モードでキー一致検索を行い、既存レコードがあれば更新、なければ新規作成する

- **Given** upsert モードのアクションが設定されたワークフロー
- **When** キー一致検索で対象アプリに1件ヒットする
- **Then** そのレコードが PUT で更新される
- **When** キー一致検索で対象アプリに0件ヒットする
- **Then** POST で新規レコードが作成される

### AC-6: キー一致検索で複数件ヒットした場合は更新をブロックしエラー通知する

- **Given** upsert または更新のみモードのアクション
- **When** キー一致検索が対象アプリで2件以上ヒットする
- **Then** 更新は行われず、`KC.Banner` にエラーメッセージが表示され、`console.error` にも記録される

### AC-7: 対象アプリへの権限不足時、カレンダー側の操作自体は成功として完了する

- **Given** ログインユーザーが対象アプリへの追加・更新権限を持たない
- **When** カレンダーで予定を作成・保存する（`calendarSave` トリガー発火）
- **Then** カレンダー側の予定作成自体は成功し、モーダルは正常に閉じる
- **And** ワークフローのアクション実行は失敗し、`KC.Banner` にエラーメッセージが表示される

### AC-8: 発火条件に一致しない場合はワークフローが実行されない

- **Given** 発火条件（フィールド=値）が設定されたワークフロー
- **When** 条件に一致しないレコードで `calendarSave` トリガーが発火する
- **Then** ワークフローのアクションは一切実行されない

### AC-9: 型不一致の未対応な組み合わせは設定保存時にブロックされる

- **Given** フィールドマッピングで CHECK_BOX（複数選択）を単一値系フィールドへマッピングしようとする
- **When** 設定画面で「保存」を実行する
- **Then** バリデーションエラーが表示され保存されない

### AC-10: config のマイグレーション（v12→v13）が既存データを保持する

- **Given** version 12 形式で保存済みの既存 config データを持つアプリ
- **When** 再編後のプラグイン設定画面を開く
- **Then** `workflows: []` が補完され、既存の他のキー（`fieldMapping` 等）は変更なく復元される

### AC-11: ワークフロー一覧・詳細編集モーダルの2階層 UI が機能する

- **Given** セクション6「ワークフロー」を開く
- **When** 「+ ワークフローを追加」を押し、詳細編集モーダルでトリガー・条件・アクションを設定して「適用」を押す
- **Then** モーダルが閉じ、ワークフロー一覧に新しい行が追加される
- **And** 画面下部の「保存」を実行すると `workflows` 配列が `setConfig` で永続化される

## 6. 想定 UX / シーケンス

### 6.1 カレンダー: 作成・更新（モーダル経由）

```
管理者がカレンダーの「+予定を追加」→ 新規作成モーダル（iframe）表示
  → kintone標準の保存ボタンをクリック（KC.Popup._attachSaveHandler が _savePending=true）
  → 保存API成功 → iframe が /show#record=N へ遷移
  → KC.Popup が _isSaveSuccessUrl を検知（load / hashchange / polling のいずれか）
     → KC.SearchFilter._invalidateRelatedRecordsCache()
     → KC.Render._refreshImmediate()
     → KC.Popup._close()（モーダルを閉じる。ここまでは既存動作、変更なし）
     → （非同期・並行）KC.Workflow.run('calendarSave', recordId)
        → KC.Api.getRecord(recordId) でレコード全体を取得
        → 該当する有効なワークフローを config.workflows から抽出
        → 各ワークフローの発火条件を判定 → 一致するものだけアクションを実行
        → アクション: 対象アプリのフィールド取得済み情報を使いレコード組み立て
           → matchKey でキー一致検索 → upsert/createOnly/updateOnly に応じ POST/PUT
        → 失敗時は KC.Banner.show(...) で通知
```

### 6.2 カレンダー: DnD（移動・リサイズ）

```
管理者が予定バーをドラッグ→ドロップ
  → 楽観的UI更新（即時反映）
  → 重複チェック（有効時）→ 重複なければ次へ
  → KC.Api.updateEvent(payload)（PUT, revision付き）
     .then(resp) 成功
        → currentEv.rev 更新（既存動作）
        → （非同期・並行）KC.Workflow.run('calendarSave', { ev: origEv, updated: payload })
           → 必要なマッピング元フィールドが KcEvent に無ければ KC.Api.getRecord(ev.id) で補完
           → 以降 §6.1 と同様
     .catch(err) 失敗 → alert + ロールバック（既存動作、変更なし。ワークフローは実行しない）
```

### 6.3 kintone 編集画面: 保存（カレンダーを介さない）

```
ユーザーがこのアプリの通常の一覧・詳細画面からレコードを編集し保存
  → app.record.edit.submit.success 発火
  → ハンドラ内で「自分は kc-modal iframe の中か？」を判定
     → iframe の中（= カレンダーモーダル経由）→ 何もしない（calendarSave 側が別途処理済み）
     → iframe の外（= 通常の kintone 画面）→ KC.Workflow.run('kintoneEditSave', event.record)
  → return event（同期・即座。ワークフロー完了を待たない）
```

### 6.4 カレンダー: 削除

```
ユーザーが削除対象レコードの詳細画面（カレンダーモーダル内 or 標準画面）で「削除」→確認
  → app.record.detail.delete.submit 発火（削除実行前・event.record にスナップショットあり）
  → KC.Workflow.run('calendarDelete', event.record) を非同期起動（await しない）
  → return event（削除処理を継続させる）
  → （非同期）ワークフロー実行 → 失敗時は次回カレンダー描画時にバナー表示
     （削除操作自体の画面には既にワークフロー結果を表示する手段がないため、
       カレンダー本体側の再読み込み時にバナーが出る形になる点に注意。§7.1 U-6）
```

### 6.5 設定画面: ワークフローの新規作成

```
管理者が設定画面「ワークフロー」セクションを開く
  → 「+ ワークフローを追加」→ 詳細編集モーダル表示
  → 名前・トリガー種別を選択
  → 発火条件を0件以上追加（フィールド選択→値選択）
  → アクションを1件以上追加
     → 対象アプリID入力 → 「フィールド取得」→ フィールド一覧セレクトが有効化
     → 動作モード選択（新規作成のみ/更新のみ/upsert）
     → upsert・更新のみの場合はキー一致設定（自アプリ⇔対象アプリのフィールド）
     → フィールドマッピング行を追加（対象アプリフィールド ← 自アプリフィールド or 固定値）
  → 「適用」→ モーダルを閉じ、ワークフロー一覧に反映（メモリ内 currentConfig.workflows 更新）
  → 画面下部「保存」または「保存して更新」→ setConfig で永続化（version 13）
```

## 8. 改訂1: トリガー再編（2026-07-15 ユーザー指示・確定）

初回実装完了後のユーザーレビューにより、トリガーの切り口を「経路別」から「操作別」に変更する。**§3.1 の3トリガー（calendarSave / calendarDelete / kintoneEditSave）は本節の定義で置き換える。**

### 8.1 新トリガー種別（操作別・経路は区別しない）

| トリガー ID | 名称 | 発火元（全経路を統合） |
|---|---|---|
| `recordCreate` | レコード作成時 | (a) カレンダー新規作成モーダルの保存成功（`KC.Popup._mode === 'create'`）、(b) `app.record.create.submit.success`（iframe 外＝標準画面） |
| `recordUpdate` | レコード更新時 | (a) DnD/リサイズの PUT 成功、(b) カレンダー編集モーダルの保存成功（`KC.Popup._mode === 'edit'`）、(c) `app.record.edit.submit.success`（iframe 外） |
| `recordDelete` | レコード削除時（物理削除） | `app.record.detail.delete.submit`（従来の `calendarDelete` と同一。削除前スナップショット利用） |

- 「カレンダー DnD か kintone 編集画面か」という**経路の区別は行わない**（ユーザー確定）。
- 二重発火防止（§3.5 の iframe マーカー）は従来通り: モーダル経由の保存は親ウィンドウ側の (a)/(b) のみが発火し、iframe 内の kintone イベントはスキップする。

### 8.2 論理削除の扱い（ユーザー確定）

- 運用上の「削除」はフィールドによる論理削除（例: ステータス=削除済）であるため、専用トリガーは設けず **`recordUpdate` ＋ 発火条件** で表現する。
- 発火セマンティクスは**状態一致・毎回発火**（削除済み状態のレコードが保存されるたびに発火する。「削除済みになった瞬間のみ」の遷移検知は行わない）。アクションが upsert であれば再発火は実害がない、という前提をユーザーと確認済み。
- 設定画面のトリガー選択部のヘルプ文に「論理削除（ステータス等での削除フラグ）を扱う場合は『レコード更新時』＋発火条件で設定する」旨を明記する。
- 遷移検知（〜になったときのみ発火）は将来拡張とし本書のスコープ外。

### 8.3 実装への影響

## 10. 改訂3: フィールド値変更トリガー＋自レコードフィールド連動アクション（2026-07-15 ユーザーヒアリング確定）

### 10.1 背景・目的

既存の `workflows`（recordCreate/recordUpdate、§8）は**保存後**に発火し、**別アプリへの書き込み**を行う仕組みである。これとは別に、ユーザーからは以下の要望がヒアリングで確定した。

- 追加/編集画面でユーザーが監視フィールドの値を変更した瞬間、または DnD で日時が変更されたときに、**保存前**に自レコードの別フィールドへ値をセットしたい。
- セットする値は「固定値」「同じレコードの他フィールドの値」「別アプリを含む他レコードのフィールド値（ルックアップ的動作）」の3種類。
- 元々 Customine で同様の処理（レコード編集時に別フィールドを更新）を組んでいたが、**DnD 操作では Customine のフックが発火しない**という制約があり、プラグインネイティブでの実現を求めている。
- 発火タイミングは「変更した瞬間（保存前）」で確定。フォーム上に即反映し、ユーザーが目視してから保存する運用。

本節は、この「フィールド連動（自動入力）」機能の要件を定義する。**既存 §1〜§9 の `workflows`（別アプリ連携アクション）とは、トリガーのタイミング（保存前 vs 保存後）とアクションの性質（自レコード読み書き vs 他アプリ書き込み）が根本的に異なるため、後述 §10.3 の通り別データモデル・別UIセクションとして設計する。**

### 10.2 現状分析（裏取り）

#### 10.2.1 kintone 公式仕様の裏取り: change イベント

cybozu developer network で以下を確認した。

- イベント名: `app.record.create.change.{フィールドコード}` / `app.record.edit.change.{フィールドコード}`（モバイルは `mobile.` 接頭辞）。
  出典: https://cybozu.dev/ja/kintone/docs/js-api/events/create/create-change-event/ 、 https://cybozu.dev/ja/kintone/docs/js-api/events/edit/edit-change-event/
- **対応フィールド型（このイベントが発火し得るフィールド型の全量）**: ラジオボタン(RADIO_BUTTON) / ドロップダウン(DROP_DOWN) / チェックボックス(CHECK_BOX) / 複数選択(MULTI_SELECT) / ユーザー選択(USER_SELECT) / 組織選択(ORGANIZATION_SELECT) / グループ選択(GROUP_SELECT) / 日付(DATE) / 時刻(TIME) / 日時(DATETIME) / 文字列1行(SINGLE_LINE_TEXT) / 数値(NUMBER) / テーブル(SUBTABLE) / ルックアップ(LOOKUP)。

- **Promise 対応について、公式ドキュメントに明記なし**（同上出典で確認済み、記載なしを確認した事実として記録）。既存の他イベント（`app.record.create.submit.success` 等）と同様に、kintone のイベントハンドラーは同期的な戻り値（`event` オブジェクトの return）を前提とした設計であり、本書では「change イベントは Promise を返せない（同期のみ）」という `kintone-rules.md` の前提と整合する挙動として扱う。ただし公式ページに直接の断定記載はないため、実装時に実機で「ハンドラーが Promise を return した場合に kintone がそれを待つか」を検証すること（§10.10 U-9）。

#### 10.2.2 kintone 公式仕様の裏取り: `kintone.app.record.set()`

出典: https://cybozu.dev/ja/kintone/docs/js-api/record/set-record-value/

- PC: `kintone.app.record.set(record)` / モバイル: `kintone.mobile.app.record.set(record)`。引数 `record` は「レコードの値を取得する」API の戻り値と同じ形式（＝ `{ record: { フィールドコード: { value: ... }, ... } }`）。
- **利用可能画面**: レコード追加画面・レコード編集画面の両方（PC/モバイル）。
- **重要な制約（委譲プロンプトの前提と食い違うため要注意）**: 公式ページに以下の記載がある（原文引用）。
  > 「`kintone.events.on()`のイベントハンドラー内では実行できません。このイベントハンドラー内で、レコードの値をセットするには、ハンドラーに渡される引数のイベントオブジェクトをreturnしてください。」
  これは「同期ソース（固定値・自レコード他フィールド）は `event.record` を書き換えて return する」という委譲プロンプトの設計方針とは整合する一方、「非同期ソース（他レコード参照）は非同期解決後に `kintone.app.record.set()` を呼ぶ」という設計方針については、**このドキュメントの文言だけでは「イベントハンドラーの同期実行スタック内で呼ぶこと」を指しているのか、「ハンドラーが return し終えた後の非同期コールバック内で呼ぶこと」まで含めて禁止しているのかが断定できない**。一般的な kintone カスタマイズの実装パターン（フィールド変更 → 外部 API 参照 → `.then()` 内で `record.set()`）は広く使われている構成ではあるが、本書の裏取り範囲では公式ドキュメント上の直接的な許可記載を確認できなかった。**この点は実機検証必須の未確認事項として扱う（§10.10 U-10）**。
  - **添付ファイルフィールドはこの API で書き換えできない**（公式明記）。
  - 計算フィールド・ルックアップフィールド・ステータス（プロセス管理）・関連レコード一覧フィールドに対する `.set()` の挙動（無視される／エラーになる／書き換え可能）は、本ページに明記がなく確認できなかった。一般に知られている制約（計算フィールドは自動再計算のため上書き不可、ステータスは専用 API 以外で変更不可、関連レコード一覧はレコードの実体を持たない参照表示のため書き込み対象にならない）はコミュニティ上の知見であり、**公式ドキュメントで断定されたものではない**。本書ではこれらの型を「セット先候補から除外する」保守的な設計を提案するが、断定はしない（§10.4.4）。
- `record` オブジェクトを「変更したいフィールドのみを含む部分オブジェクト」として渡せるか、全フィールドを含める必要があるかについても本ページに明記はなかった。既存の他社事例・実装慣行では部分オブジェクトで問題なく動作するとされるが、本書はこれも実機検証の対象とする（§10.10 U-10 に含める）。

#### 10.2.4 DnD の PUT payload 構築点（相乗り実装の技術的制約）

- `KC.DnD._commitOptimistic()`（`desktop.js:2317` 開始）は、送信フェーズで `var payload = Object.assign({}, origEv, { start: newStart, end: newEnd, rev: ... })`（`desktop.js:2422`）を組み立て、`KC.Api.updateEvent(payload)`（`desktop.js:2423`）を呼ぶ。
- `KC.Api.updateEvent(ev)`（`desktop.js:1401-1439`）は、`ev` オブジェクトに含まれる**あらかじめ決め打ちされた名前のプロパティ**（`title`/`start`/`end`/`allday`/`color`/`status`/`userMail`/`account`/`place`/`memo`）だけを見て `record[F.xxx] = { value: ... }` を組み立てる実装であり（`desktop.js:1405-1427` の `'xxx' in ev && F.xxx` という一連の条件分岐）、**任意のフィールドコードを追加で PUT ボディに混ぜる仕組みは現状存在しない**。
- したがって「同一 PUT に相乗り」させるには、`KC.Api.updateEvent()` のシグネチャを拡張する（例: 第2引数 `extraFields`（`{ フィールドコード: 値 }` 形式）を受け取り、`record` オブジェクトへマージしてから PUT する）か、`_commitOptimistic()` 側で `record` オブジェクトを直接組み立てて PUT する経路を新設する必要がある。**これは実装（builder）が対応する変更点として明記するが、本書はコード変更を行わない**。
- DnD で変わり得るのは開始/終了/終日（`KC.Config.FIELD.start` / `.end` / `.allday`）の3フィールドのみ。監視フィールドがこの3つのいずれかに一致し、かつ実際に値が変化した場合（`newStart !== origEv.start` 等の比較。終日判定は `newAllday !== origEv.allday` 相当）にのみ、DnD 経由でこのルールが評価対象になる（§10.4.3、ユーザー確定事項の論点4）。
- 「同じレコードの他フィールドの値」をセットする場合、そのソースフィールドが `KcEvent`（`_recordToEvent()`, `desktop.js:804-903`）に保持されていない可能性がある（既存 §2.1.1 と同じ制約）。DnD は元々 `async` 関数内での非同期処理のため、必要なら `KC.Api.getRecord(ev.id)`（`desktop.js:1458-1464`）で PUT 前に補完 GET を行うことが許容される（ユーザー確定の技術方針: 非同期ソースは PUT 前に await で解決する）。
- 「他レコード参照（ルックアップ）」も同様に PUT 前に await で解決する。**解決に失敗した場合（対象アプリ取得失敗・0件/複数件ヒット等）は相乗りさせず、日時変更の PUT 自体は続行する**（ユーザー確定の技術方針どおり。日時変更というユーザー操作の主目的を、付随的なフィールド連動の失敗でブロックしない）。

#### 10.2.5 モーダル iframe との関係

- iframe 内で開かれる編集/追加画面も、iframe 自身の document コンテキストで `desktop.js` が独立して評価される（§2.1.2 で確認済みの sandbox 構成、`allow-same-origin` によりロード自体は行われる）。iframe 内スクリプトが登録する `kintone.events.on('app.record.edit.change.' + code, ...)` は iframe 内の DOM 操作に対してのみ発火し、親ウィンドウの `desktop.js` インスタンス（カレンダー本体）には影響しない（別 `window` インスタンスであり `kintone` グローバルもそれぞれの document に閉じているため）。
- 既存の二重発火防止マーカー（`iframe.dataset.kcModal = '1'`, `desktop.js:1814-1815`、および `window.frameElement.dataset.kcModal === '1'` 判定 `desktop.js:11215`）は、**保存後**イベント（`recordCreate`/`recordUpdate`）の経路重複を防ぐための仕組みであり、本改訂の change イベント（**保存前**・フォーム操作起点）とは独立した関心事である。change イベントは「カレンダー経由で開いたか、通常の一覧から開いたか」によらず、そのフォームで監視フィールドが変更されれば発火するべきものであるため、**kcModal 判定によるスキップは行わない**（ユーザーヒアリングでの技術方針と整合）。

#### 10.2.6 既存 `KC.Workflow.Core` の再利用可否

- `KC.Workflow.Core._findByKey(action, sourceRecord)`（`desktop.js:7306-7334`）は「自レコードのキー値で対象アプリを検索し、更新/作成判定に使う `$id` のみ取得する」という**書き込み方向（他アプリへの反映）**のための実装であり、取得するフィールドは `['$id']` に固定されている（`desktop.js:7331`）。
- 本改訂の「他レコード参照」は**逆方向（他アプリから値を読み取り自レコードにセットする）**であり、`$id` ではなく**転記したい値フィールド**を取得する必要がある。既存 `_findByKey` をそのまま流用することはできず、クエリ構築ロジック（キー一致検索・`limit 2` で複数ヒット検知するパターン自体）は共通化・流用可能だが、`fields` パラメータと戻り値の扱いが異なる**新規ヘルパー**（例: `KC.Workflow.Core.lookupValueByKey(appId, keyFieldCode, keyValue, targetKeyFieldCode, valueFieldCode)` 相当）が必要になる（実装は builder 判断）。
- 0件/複数件ヒット時の挙動は、ユーザーヒアリングで安全側の方針が確定している（§10.4.2）: 0件＝何もしない（該当フィールドは変更しない）、複数件＝スキップ + `console.warn`（先頭を使わない）。これは既存 `_findByKey` の「複数件＝エラーとして更新ブロック」（§3.4.4, AC-6）とは扱いが異なる点に注意（書き込み方向は失敗を明示するが、読み取り方向は「安全側で何もしない」を選んでいる）。

### 10.3 データモデル方針（提案・要確認）

**提案: 新規トップレベルキー `fieldLinkRules` を新設する（既存 `workflows` 配列には統合しない）。**

理由:

1. **トリガーのタイミングが根本的に異なる**: `workflows` は保存後（GET で確定済みレコードを取得してから実行）、本機能は保存前（フォーム編集中・未確定の `event.record` を書き換える）。実行エンジンの性質（同期 vs 非同期、`event.record` 直接操作 vs REST API 呼び出し）が別物であり、無理に1つの配列・1つの `trigger.type` enum に混ぜると、`_runOne` 相当の実行部が「保存前用」「保存後用」で分岐だらけになる。
2. **許可されるアクション種別が全く異なる**: `workflows` のアクションは「対象アプリへの作成・更新（書き込み）」のみ。本機能のアクションは「自レコードのフィールドセット（＋他アプリの読み取りのみ）」に限定する必要があり（ユーザー確定の設計ガード）、この制約は**同一 UI・同一データ構造で分岐条件として持たせるより、そもそも別構造・別エディタにして「書き込みアクションの選択肢自体を存在させない」ほうが安全**である（§10.4.5）。
3. **将来のオートメーションプラグイン切り出し**（`MEMORY.md` の「オートメーションプラグイン構想」）を見据えると、保存前の同期的なフォーム連動（本機能）と、保存後の非同期的な他アプリ連携（`workflows`）は、そもそも別プラグイン・別モジュールへの分離候補として区別しておいたほうが将来の切り出しコストが低い。
4. config version は **13 のまま**でよい。`plugin/src/js/config.js:217, 3812, 3928` で確認した通り、version 13 は未リリース（未コミットの改訂2まで含めた作業ツリーの状態）であり、新規キーの追加だけであれば段階的マイグレーション（v12→v13 の1本）に手を加えるだけで足りる。

この提案は要確認事項として扱う（§10.10 U-11）。ユーザーが「既存 `workflows` の `trigger.type` に3つ目の値（例: `fieldChange`）として追加したい」という意向であれば、UI 側で「アクション種別を保存前トリガー時はセット系のみに絞り込む」バリデーション方式に変更する。

### 10.4 要件（FR）

#### 10.4.1 トリガー: フィールド値変更時（FR-9）

- トリガー種別 `fieldChange` を新設する（既存 `workflows.trigger.type` とは別の `fieldLinkRules[].watchField` として表現。§10.3 の提案採用時）。
- 監視フィールドは1ルールにつき1フィールド。選択候補の型は §10.2.1 で確認した change イベント対応型に限定する: RADIO_BUTTON / DROP_DOWN / CHECK_BOX / MULTI_SELECT / USER_SELECT / ORGANIZATION_SELECT / GROUP_SELECT / DATE / TIME / DATETIME / SINGLE_LINE_TEXT / NUMBER / SUBTABLE / LOOKUP。
  - ただし本改訂のスコープでは **SUBTABLE（テーブル内フィールド）の監視・セットは対象外**とする（テーブル行単位の値構造は `event.record` 内でネストされ、UI・バリデーションの複雑度が大きく上がるため）。設定画面のフィールド選択でテーブル内フィールドは選択肢から除外する。
- 発火経路:
  (a) 追加/編集画面で監視フィールドの値をユーザーが変更した瞬間（`app.record.create.change.<code>` / `app.record.edit.change.<code>`）。
  (b) DnD で監視フィールドに対応する開始/終了/終日のいずれかが実際に変化したとき（§10.2.4、§10.4.3）。
- 発火条件（AND、0件以上）は既存 `workflows` の「フィールド選択→値選択」パターン（`buildWorkflowConditionRow`, `config.js:1961` 等）を流用可能。ただし本機能に条件を持たせるかどうかは要確認（§10.10 U-13）。

#### 10.4.2 アクション: 自レコードのフィールドをセット（FR-10）

1ルールにつき1件以上の「セットアクション」を配列で保持する（実行順序＝配列順の逐次適用）。各セットアクションは以下の値ソースのいずれか1つを持つ。

| ソース種別 | 内容 | 反映方法 |
|---|---|---|
| `fixed`（固定値） | 設定画面で入力した固定文字列 | 同期（`event.record` 書き換え or DnD payload 相乗り） |
| `selfField`（自レコード他フィールド） | 同じレコードの別フィールドの現在値をコピー | 同期。change イベントの `event.record` から直接読み取れる。DnD 経由の場合、`KcEvent` に値がなければ `KC.Api.getRecord()` で補完（§10.2.4） |
| `lookup`（他レコード参照） | 別アプリ（または自アプリの他レコード）をキー一致で検索し、ヒットしたレコードの指定フィールド値を転記 | 非同期。change イベント経路: ハンドラは即 return し、非同期解決後に `kintone.app.record.set()` で反映（§10.2.2 の未確認事項あり）。DnD 経路: PUT 前に await で解決（§10.2.4） |

`lookup` の設定項目:

- 参照先アプリ ID（自アプリでも別アプリでも可）
- 自レコード側キーフィールドコード（既定値: 監視フィールド自身のコード。変更可能とし、監視フィールドとは別のフィールドをキーに使うケースにも対応する）
- 参照先アプリ側キーフィールドコード
- 参照先アプリ側の転記元フィールドコード（値を取ってくるフィールド）

0件/複数件ヒット時の挙動（ユーザー確定・安全側）:

- 0件ヒット: 何もしない（セット先フィールドは変更しない。既存値を維持する）。
- 複数件ヒット: セットをスキップし `console.warn` に記録する（先頭レコードを使わない。§3.4.4 の書き込み方向とは異なり、読み取り方向は「失敗を通知しつつ変更しない」を安全側デフォルトとする）。

#### 10.4.3 DnD での「監視フィールド」の意味（FR-11・仕様として明記）

- DnD で実際に変化しうるのは開始/終了/終日の3フィールドのみ。監視フィールドがこれら以外（例: ステータスや文字列フィールド）の場合、**DnD 操作ではこのルールは発火しない**（正常仕様。ユーザーが追加/編集画面でその他フィールドを変更した場合にのみ発火する）。
- DnD 経由で発火する場合も、実際に値が変化した場合のみ評価する（例: 終了だけを伸ばすリサイズで開始が変わらない場合、監視フィールドが開始日時のルールは評価しない）。

#### 10.4.4 セット先フィールドの制約（FR-12）

セット先フィールド候補から以下の型を除外する（設定画面の選択肢に表示しない）。

| 型 | 除外理由 | 確度 |
|---|---|---|
| 添付ファイル(FILE) | `kintone.app.record.set()` で書き換え不可と公式に明記（§10.2.2） | 確定（公式明記） |
| 計算(CALC) | 自動計算のため外部からの値セットは意味を持たない | 一般に知られている制約。公式ページでの断定記載は未確認 |
| ルックアップ(LOOKUP) | 専用のルックアップ取得機構（【取得】ボタン相当の動作）を持ち、単純な値上書きの対象として扱うと挙動が不定 | 保守的に除外。公式ページでの断定記載は未確認 |
| ステータス(STATUS・プロセス管理) | 通常のフィールド値セットとは別の専用 API（ステータス変更 API）で変更するものであり、フォーム上の `.set()` 対象として想定されていない | 一般に知られている制約。公式ページでの断定記載は未確認 |
| カテゴリー(CATEGORY) | プロセス管理と同様、レコードの分類メタ情報でありフィールド値としての単純セット対象ではない | 一般に知られている制約。未確認 |
| 関連レコード一覧(REFERENCE_TABLE) | レコード実体を持たない参照表示であり、セットする値という概念がない | 構造上除外（設定不能） |
| サブテーブル内フィールド | 本改訂のスコープ外（§10.4.1） | スコープ外として除外 |

上記のうち「一般に知られている制約」に分類したものは、公式ドキュメントで断定的な記載を確認できなかった（§10.2.2）。実装時に実機で除外の妥当性を検証すること（§10.10 U-10 に含める）。

#### 10.4.5 設計ガード: 書き込みアクションの禁止（NFR-5・確定方針）

- この保存前トリガー（`fieldLinkRules`）には、既存の別アプリ書き込みアクション（createOnly/updateOnly/upsert）を**紐付けさせない**。
- §10.3 の提案（別トップレベルキー・別UIセクション）を採用する場合、この制約は**構造的に担保される**（`fieldLinkRules` のエディタ UI には、そもそも「対象アプリへの作成・更新」を選択する UI 自体が存在しない。バリデーションで弾くのではなく、選択肢として提示しないことでミス設定自体を発生させない設計）。
- 目的: 編集キャンセル時（保存せずに画面を離脱した場合）に外部（他アプリ）へ何も書き込まれていない状態を保証するため。`lookup` ソースは**読み取り専用**（GET のみ）であり、この制約に抵触しない。

#### 10.4.6 実行順序・複数ルール（FR-13）

- 1つの監視フィールドに対して複数の `fieldLinkRules` を定義できる。実行順序は一覧内の並び順（DnD 並び替え）に従う（既存 `workflows` と同じ思想）。
- 同一ルール内の複数セットアクションは配列順に逐次適用する。
- 複数ルールが同一のセット先フィールドを異なる値で更新しようとする場合、後から実行されたルールの値で上書きされる（後勝ち）。これは仕様上の制約として明記し、自動検知・警告は行わない（§10.11 リスク）。

#### 10.4.7 エラーハンドリング・通知（NFR-6）

- change イベント経路: `lookup` 解決失敗時（対象アプリ取得エラー・複数件ヒット等）は `console.error`（複数件ヒットは `console.warn`）に記録するのみとする。カレンダー画面ではないため既存 `KC.Banner`（`desktop.js:7027` 付近）は使えない。追加/編集画面上に簡易な通知 UI（例: フィールド下のインラインエラー表示）を出すかどうかは、実装コスト対効果の観点から本改訂ではスコープ外とし、`console.error` のみに留める（ユーザーヒアリングの想定「簡素に」と整合）。
- DnD 経路: `lookup` 解決失敗時は相乗りをスキップし、PUT はそのまま続行する（§10.2.4）。失敗の記録は `console.warn` に留め、DnD 操作自体のバナー（重複チェック用）とは競合させない。

### 10.7 受入基準（AC-15〜）

Given/When/Then 形式で記述する。

- **AC-15**: 追加/編集画面で監視フィールドの値を変更すると、固定値ソースのセットアクションが即座に反映される
  - Given 監視フィールド A・セット先フィールド B（固定値「X」）のルールが有効
  - When ユーザーがフォーム上でフィールド A の値を変更する
  - Then 保存せずにフィールド B の表示が「X」に即座に変わる

- **AC-16**: 自レコード他フィールド値ソースが同期的に反映される
  - Given 監視フィールド A・セット先フィールド B（`selfField`＝フィールド C の値）のルールが有効
  - When ユーザーがフィールド A を変更する
  - Then フィールド B にフィールド C の現在値が即座にコピーされる

- **AC-17**: 他レコード参照（lookup）が非同期で解決されフォームに反映される
  - Given 監視フィールド A・セット先フィールド B（`lookup`＝別アプリをキー一致検索）のルールが有効
  - When ユーザーがフィールド A を変更する
  - Then 変更直後はフィールド B は変化せず、検索完了後にフィールド B へ値がセットされる
  - And この反映は `change` イベントが再度発火する連鎖を起こさない

- **AC-18**: DnD で監視フィールド（開始/終了/終日）が変化した場合、セットアクションが同一 PUT に相乗りする
  - Given 監視フィールドが開始日時のルールが有効
  - When 予定を DnD で移動し PUT が送信される
  - Then 同一 PUT のレコードボディにセットアクション対象フィールドの値が含まれる
  - And 監視フィールドが開始/終了/終日以外のルールは DnD では発火しない

- **AC-19**: lookup 解決失敗時、DnD の日時変更は継続される
  - Given lookup ソースを含むルールが有効で、参照先アプリが取得エラーになる状態
  - When DnD で監視フィールドを変更する
  - Then 日時変更の PUT は正常に送信される（セットアクションのみスキップされる）
  - And `console.warn`/`console.error` に記録される

- **AC-20**: lookup の複数件ヒットはセットをスキップする
  - Given 参照先アプリにキー一致するレコードが2件存在する
  - When 監視フィールドを変更する
  - Then セット先フィールドは変更されず、`console.warn` に記録される

- **AC-21**: セット先フィールド候補から除外型が選択できない
  - Given ルール編集モーダルでセット先フィールドを選ぼうとする
  - When フィールド選択セレクトを開く
  - Then 添付ファイル・計算・ルックアップ・ステータス・関連レコード一覧・サブテーブル内フィールドは選択肢に表示されない

- **AC-22**: このトリガーに別アプリ書き込みアクションを設定するUIが存在しない
  - Given ルール編集モーダルを開く
  - When セットアクションの種別を確認する
  - Then 「対象アプリへの作成・更新」に相当する選択肢は一切表示されない（固定値/自レコードフィールド/他レコード参照の3種のみ）

- **AC-23**: iframe モーダル経由の編集でも change イベント連動が機能する
  - Given カレンダーの編集モーダル（iframe）を開く
  - When iframe 内で監視フィールドを変更する
  - Then kcModal 判定によるスキップなしにセットアクションが反映される

### 10.9 想定 UX / シーケンス

#### 10.9.1 追加/編集画面（固定値・自レコードフィールド＝同期ソース）

```
ユーザーがフォーム上で監視フィールドの値を変更
  → app.record.create.change.<code> / app.record.edit.change.<code> 発火
  → ハンドラ内で該当する有効な fieldLinkRules を検索（KC.Config.FIELD_LINK_RULES 相当のキャッシュから）
  → 発火条件（あれば）を判定
  → セットアクションのうち sourceType='fixed'/'selfField' のものを event.record 上で直接書き換え
  → return event（同期・即座。フォームに即反映される）
```

#### 10.9.2 追加/編集画面（他レコード参照＝非同期ソース）

```
ユーザーが監視フィールドの値を変更
  → change イベント発火
  → 同期ソースは §10.9.1 と同様に即時反映して return event
  → sourceType='lookup' のセットアクションがある場合、ハンドラは該当フィールドをそのまま return し

  → 非同期でキー一致検索（対象アプリへ GET）
  → 0件: 何もしない / 複数件: console.warn のみ / 1件: 値を確定
  → 解決後、kintone.app.record.set({ record: { <セット先フィールド>: { value: ... } } }) でフォームに反映

```

#### 10.9.3 DnD（移動・リサイズ）

```
ユーザーが予定バーをドラッグ→ドロップ
  → 楽観的UI更新（即時反映、既存動作）
  → 重複チェック（有効時、既存動作）
  → 監視フィールドが開始/終了/終日のいずれかで、かつ実際に値が変化した fieldLinkRules を評価
     → sourceType='fixed'/'selfField' は同期的に値を確定（selfField は KcEvent 不足時 getRecord で補完）
     → sourceType='lookup' は PUT 前に await で解決（失敗時はこのセットのみスキップ）
  → 解決済みのセット値を PUT のレコードボディに相乗りさせて送信（KC.Api.updateEvent 拡張、または record 直接構築。実装は builder 判断）
  → PUT 成功 → 既存の recordUpdate トリガー（§8）は従来通り非同期・fire-and-forgetで実行
  → PUT 失敗 → 既存動作（ロールバック）。セットアクションも反映されない（PUT 自体が失敗しているため）
```

#### 10.13.1 U-10 スパイク結果（実機 app891 編集画面・Chrome コンソールで検証済み）

| 検証項目 | 結果 |
|---|---|
| (a) change ハンドラ return 後の非同期コールバックから `kintone.app.record.set()` | **動作する**（フォームに即反映）。lookup 方式は実現可能 |
| (b) 部分オブジェクト（変更フィールドのみ）での `set()` | **不可**。`event.record['xxx'].type が不正です` エラー。しかも**同期例外にならず**（try/catch で捕捉不能）、非同期にユーザー向け赤バナーが出て値も反映されない。**実装は必ず `kintone.app.record.get()` → value 書き換え → `set(全体)` パターンを使うこと** |

#### 10.13.2 (c) を受けたループ対策（必須要件に昇格）

- `kintone.app.record.set()` は change イベントを発火させるため、「ルールAが監視フィールドXの変更でフィールドYをセット → Yを監視するルールBが発火 → ルールBがXをセット → …」の**無限ループが成立し得る**。
- 対応（両方実装）:
  1. **再入ガード**: ルール実行によるセット中はモジュールスコープのフラグ（例: `_applyingRules = true`）を立て、フラグ中に発火した change イベントではルール評価をスキップする（同期セット・非同期 set() の完了までカバー。非同期は set() 呼び出し直前〜直後のフラグ管理に注意）
  2. **設定保存時の循環警告**: 「ルールAのセット先フィールド ∈ 他ルールの監視フィールド」となる組み合わせを検出したら、設定画面で警告を表示する（保存ブロックまではしない。再入ガードが実行時の安全網になるため）
- なお change ハンドラ内で `event.record` を書き換えて return する同期パスが change を再発火させるかは今回未検証。再入ガードは同期パスにも一律適用することで、挙動差に依存しない設計とする。

#### 10.13.3 U-9 / U-13 の確定

- **U-9**: 解消。非同期処理は (a) の「ハンドラは即 return → 非同期解決後に `set()`」方式で実現するため、change ハンドラの Promise 対応有無に依存しない設計となった。
- **U-13（ユーザー確定）**: 発火条件を**付ける**。さらに条件モデルを **AND/OR 複合条件**に拡張する。この拡張は fieldLinkRules だけでなく**既存 workflows の発火条件にも適用**する（ユーザー指示「他の条件設定でもそうだが」）。
  - モデル: **条件グループの配列（グループ内=AND、グループ間=OR）**。「いずれかのグループの条件がすべて成立したら発火」。
  - データ形式: 既存 `conditions: [{fieldCode, fieldType, value}]` を `conditionGroups: [[{fieldCode, fieldType, value}, ...], ...]` に変更（v13 未リリースのためマイグレーション不要。空配列 or 未定義 = 無条件で発火、は従来通り）。
  - UI: 既存の条件行リストを「グループ」単位で囲み、「+ 条件を追加（AND）」「+ グループを追加（OR）」の2ボタン構成。フィルタ設定（グループ内OR・グループ間AND）とは論理が**逆**であるため、ヘルプ文で明示すること。
  - `KC.Workflow.Core.matchesConditions` は conditionGroups 対応に改修（Core 内で完結、後方互換不要）。

#### 10.13.4 U-11/U-12/U-14/U-15 の確定（管理者裁量）

- U-11: `fieldLinkRules` 別キー方式を採用（§10.3 提案通り）。
- U-12: 保守的除外リストで開始（§10.4.4 提案通り）。
- U-14: 後勝ち＋設定画面ヘルプで明記。
- U-15: builder が実装時に `updateEvent` 全呼び出し元を洗い出し、後方互換（拡張引数省略時は完全に従来動作）を担保する。
- 軽量 config ロード（§10.2.3）は `workflows` と `fieldLinkRules` の両方を対象にし、**標準画面で workflows が発火しないバグの修正を兼ねる**。

## 11. 改訂4: フィールド連動のワークフロー統合（2026-07-15 ユーザー指示・確定）

改訂3で別キー `fieldLinkRules` として実装したフィールド連動を、**`workflows` 配列に統合し、設定セクションも1つにまとめる**（ユーザー指示）。§10.3 の U-11 判断（別キー方式）を本改訂で上書きする。config v13 は未リリース（未push・実機未導入）のためマイグレーション不要で構造変更できる。

### 11.1 統合後のデータモデル（config v13 のまま）

```jsonc
"workflows": [
  {
    "id": "wf_...", "name": "...", "enabled": true,
    "trigger": {
      "type": "recordCreate" | "recordUpdate" | "fieldChange",
      "watchFieldCode": "..."   // fieldChange のみ必須。他は不要
    },
    "conditionGroups": [[ {fieldCode, fieldType, value}, ... ], ...],  // 共通（グループ内AND・グループ間OR）
    "actions": [
      // トリガーにより許可される type が異なる
      { "type": "appAction", /* 既存の targetAppId/mode/matchKey/fieldMappings/continueOnError */ },
      { "type": "setField",  /* 既存 fieldLinkRules の setAction: targetFieldCode/sourceType(fixed|selfField|lookup)/... */ }
    ]
  }
]
```

- `fieldLinkRules` トップレベルキーは**廃止**。
- 防御的変換: 読込時に `fieldLinkRules` が存在した場合（中間ビルドを導入した環境対策）、各ルールを `trigger.type='fieldChange'` のワークフローへ変換して `workflows` に取り込み、キーを破棄する（正式リリース前のため本変換は簡易でよい）。
- アクションの `type` 識別子を新設。既存保存データは v13 未リリースのため考慮不要だが、`type` 未定義の action は `appAction` とみなす防御は入れてよい。

### 11.2 トリガーとアクション種別の対応（設計ガードの継承）

| trigger.type | 許可される action.type | 実行系 |
|---|---|---|
| recordCreate / recordUpdate | `appAction` のみ | KC.Workflow（保存後・非同期） |
| fieldChange | `setField` のみ | KC.FieldLink（保存前・フォーム/DnD相乗り） |

- §10.4.5 の設計ガード（保存前トリガーに書き込みアクションを紐付けない）は、**編集モーダルのアクションUIをトリガー種別で丸ごと切り替える**ことで維持する（fieldChange 選択時は appAction の設定UIが存在しない）。
- トリガー種別を変更した際、設定済みアクションが新トリガーで無効になる場合は確認ダイアログを出し、了承時にアクションをクリアする。

### 11.3 実行エンジンへの影響（最小化）

- KC.Workflow（保存後）と KC.FieldLink（保存前）の2系統は**そのまま維持**。軽量ロード処理が `workflows` を trigger.type で振り分け、recordCreate/recordUpdate 系を KC.Workflow 用に、fieldChange 系を KC.FieldLink 用（内部形式へマップ）に供給する。
- 再入ガード・直列化・DnD相乗り・二段防御・conditionGroups 評価など改訂3の実装・検証結果はすべて有効。
- change イベントの動的登録は fieldChange ワークフローの watchFieldCode 一覧から行う（従来と同等）。

### 11.4 設定画面

- セクション7「フィールド連動」を**廃止**し、セクション6「ワークフロー」に一本化。一覧は全トリガー種別を混在表示（トリガー種別バッジで区別。実行順序は同一トリガー種別内でのみ意味を持つ）。
- 編集モーダル: トリガーセレクトに「フィールド値変更時」を追加し、選択時のみ監視フィールドセレクトを表示。アクション領域はトリガー種別で切替（既存の setField エディタ部品を移設・流用）。
- 循環警告・セット先除外・lookup 設定UIなど改訂3の部品はそのまま流用する。

### 11.6 改訂4追加指示（2026-07-15 ユーザー指示・確定）

#### 11.6.1 条件設定の AND/OR 自由化

§10.13.3 の固定論理（グループ内=AND・グループ間=OR）を廃止し、**両方をユーザーが選択可能**にする。

- データ形式（v13 のまま・未リリースのためマイグレーション不要）:
  ```jsonc
  "conditionGroups": [
    { "op": "and" | "or", "conditions": [ {fieldCode, fieldType, value}, ... ] },
    ...
  ],
  "conditionGroupsJoin": "and" | "or"   // グループ間の結合（ワークフロー単位で1つ）
  ```
- 既定値: `op: "and"`、`conditionGroupsJoin: "or"`（従来の固定論理と同じ挙動）
- 防御的フォールバック: 旧「配列の配列」形式が来た場合は各グループ `op:'and'`・`join:'or'` として解釈
- `KC.Workflow.Core.matchesConditions` を新形式対応に改修（グループ内は op に従い every/some、グループ間は join に従い every/some。空グループ・空配列=無条件で発火、は従来通り）
- UI: 各グループのヘッダに「すべて満たす（AND）／いずれかを満たす（OR）」セレクト、グループ一覧の上部（または各グループ間）にグループ間結合の AND/OR セレクトを1つ配置。ヘルプ文を新論理に合わせて全面更新（フィルタ設定との論理差の注記は不要になる場合は削除してよい）
- 保存前後（KC.Workflow / KC.FieldLink）の両実行系・fieldChange/appAction の全トリガーに適用

## 12. 改訂5: 条件ツリー化（グループの入れ子・2026-07-15 ユーザー指示・確定）

§11.6.1 の2階層モデル（conditionGroups + conditionGroupsJoin）を廃止し、**再帰的な条件ツリー**に置き換える。ユーザー要望: 「グループをグループで囲める」「そのグループにも AND/OR を付けられる」「グループへの出し入れを UI 上で自由に行える」。

### 12.1 データモデル（config v13 のまま・未リリースのためマイグレーション不要）

```jsonc
"conditionTree": {
  "op": "and" | "or",
  "children": [
    { "type": "condition", "fieldCode": "...", "fieldType": "...", "value": "..." },
    { "type": "group", "op": "and" | "or", "children": [ /* 再帰 */ ] }
  ]
}
```

- ルートは常に1つのグループノード（op + children）。`conditionGroups` / `conditionGroupsJoin` キーは廃止。
- **データ形式としては深さ無制限**。UI 上の新規ネスト作成は**3階層まで**に制限する（ルート=1階層目。深さ4以上のデータが存在した場合も評価・表示は行い、そこへの新規グループ追加のみ不可とする）。
- 防御的正規化（読込時に旧3形式をツリーへ変換）:
  - 最古フラット配列 → `{op:'and', children:[条件...]}`
  - 配列の配列（§10.13.3） → `{op:'or', children:[{type:'group',op:'and',children:[...]}, ...]}`
  - `{op,conditions}`+`conditionGroupsJoin`（§11.6.1） → `{op:join, children:[{type:'group',op:g.op,children:[...]}, ...]}`
- 空 children のグループ・conditionTree 未定義 = 無条件で発火（従来通り）。

### 12.2 評価ロジック

- `KC.Workflow.Core.matchesConditions(record, tree)` を再帰評価に改修: group ノードは `op` に従い children を every/some、condition ノードは既存の `_matchesOneCondition`。空 children = true。
- 呼び出し3箇所（`_runOne` / `KC.FieldLink.onChange` / `resolveForDnd`）は tree を渡す形に単純化（join 引数は廃止）。

### 12.3 UI（確定方針: ボタン方式＋グループ内 DnD）

- グループはネストに応じたインデント付きカードで再帰描画。各グループヘッダ: AND/OR セレクト（すべて満たす/いずれかを満たす）＋「+ 条件」「+ グループ」（深さ3のグループでは「+ グループ」を無効化）＋「グループを解除」（子要素を親へ展開して自身を消す）＋「グループを削除」（子要素ごと削除・confirm あり・ラベル付きボタン §11.6.2 踏襲）。ルートグループは解除・削除不可。
- **出し入れはボタン方式**:
  - 各行（条件・グループ共通）に「↰ 外へ」（親グループへ移動。ルート直下では非表示）
  - 各行に「⊕ グループ化」(その行を新しいグループで包む。深さ上限で無効化)
- **同一グループ内の並び替えは既存 DnD**（attachRowDragEvents 流用）。階層をまたぐ DnD は実装しない（確定）。
- 保存（collect）・復元（apply）は再帰で往復。

### 12.4 受入基準（追加）

- **AC-29**: `(A AND B) OR (C AND (D OR E))` 相当のツリーを UI で作成→保存→再読込で構造が完全に復元される
- **AC-30**: 実行時評価がツリー構造・各ノードの op に厳密に従う（保存前後の両実行系）
- **AC-31**: 「外へ」「グループ化」「グループを解除」の操作でツリーが意図通り変形し、操作後も DnD 並び替え・収集が正常
- **AC-32**: 深さ3のグループ内では「+ グループ」「グループ化」が無効化される
- **AC-33**: 旧3形式（フラット/配列の配列/op+join）の保存データが読込時にツリーへ正規化され従来と同じ評価結果になる

## 13. 改訂6: 時刻条件の追加（2026-07-16 ユーザー指示・確定）

発火条件の条件ツリー（§12）に、フィールド値の一致以外の**時刻ベースの条件ノード**を追加する。背景: 当初「定期実行」の要望があったが、ブラウザプラグインでは時刻起点の確実な実行を保証できないため放念（確実な定期実行が必要になった場合は Customine Job Runner 等の外部基盤を利用する方針）。トリガー発火時に評価する「時刻条件」のみを本改訂で追加する。

### 13.1 条件ノードの種別（kind）の導入

条件ノード（type:'condition'）に `kind` 識別子を追加する。

| kind | 意味 | 保存形式 |
|---|---|---|
| `fieldValue`（既定・既存） | フィールド値の完全一致（従来通り） | `{type:'condition', kind:'fieldValue', fieldCode, fieldType, value}`。**kind 未定義は fieldValue とみなす**（既存データの後方互換） |
| `timeRange`（新規） | **現在時刻**（評価時点のブラウザローカル時刻）が指定範囲内 | `{type:'condition', kind:'timeRange', from:'HH:MM', to:'HH:MM'}`。**日跨ぎ対応**（例: 22:00〜06:00 は「22時以降 または 6時前」と解釈） |
| `fieldTimeCompare`（新規） | レコードの日時/日付フィールドと現在日時の比較 | `{type:'condition', kind:'fieldTimeCompare', fieldCode, fieldType, comparison:'past'|'future'}`。past=フィールド値が現在より過去、future=未来。DATETIME は UTC ISO 値を Date 比較、DATE は当日 00:00（ローカル）基準 |

- 未知の kind は**不成立（false）扱い＋console.warn**（安全側。未知 sourceType のスキップ方針と整合）
- 評価は `_matchesOneCondition`（KC.Workflow.Core）に kind 分岐を追加。両実行系（保存後 KC.Workflow／保存前 KC.FieldLink）・全トリガーに自動適用（matchesConditions 共有のため）
- タイムゾーンは**評価するブラウザのローカル時刻**である旨を設定画面のヘルプに明記（サーバー時刻ではない）

### 13.2 設定画面 UI

- 条件行の先頭に「条件の種類」セレクトを追加: 「フィールドの値」（既定）／「現在時刻が範囲内」／「日時フィールドと現在の比較」
- 種類の切替で行内の入力部を差し替え:
  - フィールドの値: 従来通り（フィールド select ＋ 値）
  - 現在時刻が範囲内: `<input type="time">` ×2（開始・終了）。日跨ぎ可の旨をプレースホルダかヒントで示す
  - 日時フィールドと現在の比較: 日時系フィールド（DATETIME/DATE）限定の select ＋「より過去／より未来」select
- collect/apply・条件ツリーの出し入れ操作（外へ/グループ化等）は kind によらず同一に扱う
- バリデーション: timeRange は from/to 必須、fieldTimeCompare はフィールド必須

### 13.3 受入基準（追加）

- **AC-34**: timeRange 条件が現在時刻で正しく判定される（範囲内=成立、範囲外=不成立、日跨ぎ範囲も正しい）
- **AC-35**: fieldTimeCompare 条件が DATETIME/DATE フィールドと現在日時の過去/未来を正しく判定する
- **AC-36**: kind 未定義の既存条件（fieldValue 相当）が従来通り動作する（後方互換）
- **AC-37**: 時刻条件を含む条件ツリーが保存→再読込で完全復元され、グループ出し入れ操作も正常

## 14. 改訂7: 保存後モーダルクローズ動作の設定（2026-07-17 ユーザー指示・確定）

### 14.1 背景

カレンダーのモーダル（iframe）で保存すると、プラグインは保存成功の URL 遷移を検知して**即座に iframe を破棄**する（§2.1.2）。iframe 破棄はその中で実行中の全 JS（Customine の「保存した直後」ジョブ等）を強制終了させるため、保存後に数秒かかるカスタマイズ処理（ループでのレコード追加・Slack 通知等）が途中で殺される実害が確認された（実例: Customine ページ9 ジョブ）。

### 14.2 要件

プラグイン設定に**アプリ全体設定「保存後のモーダル動作」**を追加する（config v13 のまま新キー追加）。

```jsonc
"modalCloseBehavior": { "mode": "immediate" | "delay" | "manual", "delaySeconds": 5 }
```

| mode | 動作 |
|---|---|
| `immediate`（既定・従来互換） | 現行通り、保存成功検知で即クローズ |
| `delay` | 保存成功検知後、`delaySeconds` 秒（1〜60、既定5）待ってからクローズ。待機中は iframe を維持（Customine 等の後続処理を生かす）。カレンダーの再描画・ワークフロー起動は従来通り検知直後に実施 |
| `manual` | 自動クローズしない。カレンダー再描画・ワークフロー起動は検知直後に実施し、iframe はユーザーが×/ESC/背景クリックで閉じるまで維持 |

- 適用対象は**保存成功後の自動クローズのみ**。キャンセル・許可外URL遷移などの既存クローズ経路は変更しない
- delay 待機中にユーザーが手動で閉じる操作をした場合は即クローズ（待機をキャンセル）
- 設定 UI: セクション1「基本設定」にサブセクション「モーダル動作」を追加（ラジオ3択＋delay 時のみ秒数入力）。ヘルプ文に「保存直後に動くカスタマイズ（Customine等）がある場合は待機または手動クローズを推奨」と明記
- 旧 config（キーなし）は immediate 扱い（マイグレーション不要・防御的既定値）

### 14.3 受入基準

- **AC-38**: 既定（キーなし/immediate）で従来と同一動作
- **AC-39**: delay 設定時、保存成功から指定秒数の間 iframe が破棄されず、その間に iframe 内で実行中の処理が完走できる。待機後に自動クローズ
- **AC-40**: manual 設定時、保存成功後も iframe が維持され、ユーザー操作で閉じられる。カレンダー再描画とワークフロー起動は保存成功検知直後に行われる
- **AC-41**: delay 待機中の手動クローズが即座に機能する
