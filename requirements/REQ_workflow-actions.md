**文書番号**: REQ_workflow-actions

**作成者**: designer（サブエージェント）
**ステータス**: 設計完了（未実装・ユーザー確認待ち事項あり）
**入力資料**: 管理者からの委譲プロンプト（ユーザーヒアリング確定事項を含む）
**対象ファイル（実装時）**:
- `plugin/src/js/desktop.js`（カレンダー本体。トリガーフック・ワークフロー実行エンジン）
- `plugin/src/js/config.js`（設定画面ロジック。config version 13 へ）
- `plugin/src/html/config.html`（設定画面。セクション6「ワークフロー」新設 + 詳細編集モーダル新設）
- `plugin/src/css/config.css`（新規 UI のスタイル）

**方針（ユーザーヒアリングで確定・変更禁止）**:
- フローUI: **ステップ列挙型**（分岐なしの直列フロー）。既存のテーブルUIパターン（行追加/削除/DnD並び替え）を踏襲する。
- 実行権限: **ログインユーザー権限**（`kintone.api` をそのまま使用。API トークン認証は対象外）。
- トリガーは **3種**: (1) カレンダー: 作成・更新、(2) カレンダー: 削除、(3) kintone 編集画面: 保存。
- 更新先レコード特定は **キー一致検索**（upsert オプションを含む）。
- 発火条件はユーザーが定義可能（フィールド選択→値選択の UI）。
- **REST API 経由の外部更新はトリガー対象外**（プラグイン＝ブラウザ JS では検知不可のため）。
- **分岐・並列フロー、Webhook 発信、メール送信等のアクション種別拡張は将来拡張とし今回スコープ外**。

## 1. 背景・目的

kintone-calendar プラグインで管理する予定（レコード）の作成・更新・削除を起点に、**別の kintone アプリへレコードの追加・更新を行いたい**という要望がある。

`kintone-rules.md` の実装方針優先順位（Customine 最優先）に照らすと、まず Customine の利用可否を検討すべきだが、本要望は次の理由により **Customine を経由せずプラグイン内で完結させる** ことが確定事項としてヒアリング済みである。

- カレンダー独自の3種類のトリガー（DnD/リサイズ、モーダル経由の保存、kintone 標準編集画面の保存）を一元的に捕捉する必要があり、これらは既に `desktop.js` 内に実装済みのイベント処理・DOM 監視ロジックと密結合している（§2 参照）。Customine 側から見ると DnD 操作はカスタマイズ JS 内で完結する UI 操作であり、Customine のイベントフックの対象にならない。
- プラグインの設定情報（フィールドマッピング・重複チェック設定等）と同じ config ストア (`kintone.plugin.app.setConfig`) に、ワークフロー定義も一元管理したいという運用上の要望（設定の一箇所集約）。
- `PLUGIN_DISCUSSION.md` で示されている通り、本プラグインは「非エンジニアへの設定委譲」を目指す方向で設計されており、ワークフロー設定も同一の GUI 上で完結させることが既定路線と整合する。

本書は、この「ワークフロー」機能の要件定義（トリガー・条件・アクションの構成、config データ形式、既存コードへの差し込み点、UI 配置）を確定するために作成する。実装（コード変更）は行わない。

## 2. 現状分析

### 2.1 カレンダー側の3つの保存・削除経路（裏取り済み）

ユーザーヒアリングでは「新規作成モーダル、DnD/リサイズ、編集モーダル経由の保存」がまとめて1つのトリガー種別（トリガー1）とされているが、実装を裏取りした結果、**これらは技術的には2つの異なる検知メカニズムに分かれる**ことが判明した。加えて、削除・kintone標準編集画面の保存についても既存コードとの整合性を確認した。

#### 2.1.1 DnD（移動・リサイズ）

- 実体: `KC.DnD` 内 `_commitOptimistic()`（`desktop.js:2264-2385`）。
- 重複チェック（有効時）を通過した後、`KC.Api.updateEvent(payload)`（`desktop.js:2370`、PUT `/k/v1/record.json`、楽観ロック `revision` 付き。`updateEvent` 本体は `desktop.js:1391-1428`）を呼ぶ。
- **フック候補**: `updateEvent(payload).then(function (resp) { ... })`（`desktop.js:2371-2378`）の成功コールバック内。ここは PUT が **サーバー側で成功したことが確定した後** の地点であり、`payload`（更新後の start/end 等）と `origEv`（更新前の KcEvent）の両方にアクセスできる。
- 送信は非同期・非ブロッキング（`.then/.catch`、`await` していない。`desktop.js:2366`のコメント「API を非同期送信（楽観的: レスポンスを待たない）」）。ワークフロー実行もこの非同期性を踏襲すべき（§3.6 NFR-2）。
- **注意**: `KcEvent`（`_recordToEvent()`, `desktop.js:804-903`）が保持するフィールドは、タイトル/開始/終了/終日/色/場所/メール/アカウント/メモ/ステータスと、権限・フィルタ設定で指定されたフィールドの値（`permissionFields` / `valueFields`）のみ。ワークフローのフィールドマッピングで **任意のフィールド** を参照したい場合、`KcEvent` に値が無い可能性が高く、`KC.Api.getRecord(ev.id)`（`desktop.js:1447-1453`）による再取得が必要になるケースがある（§3.4.3 参照）。

#### 2.1.2 新規作成モーダル・編集モーダル経由の保存

- `KC.Popup.openCreate()`（`desktop.js:2024-2052`）/ `openEdit()`（`desktop.js:2059-2082`）は、kintone 標準の編集・詳細画面（`/k/{appId}/edit` または `/k/{appId}/show#record=N`）を **同一 DOM 内 iframe** で開く（`window.open` ではない。コメント `desktop.js:1461-1467`）。
- iframe は `sandbox="allow-same-origin allow-scripts allow-forms allow-popups allow-modals allow-downloads"`（`desktop.js:1810-1813`）で、同一オリジン（cybozu.com）のため `iframe.contentDocument` に親からアクセス可能。
- 保存検知は kintone の `kintone.events` を使わず、**親ウィンドウ側で完結する独自メカニズム**で行っている:
  1. iframe 内の「保存」ボタンをテキスト一致で検出し、クリックで `KC.Popup._savePending = true` をセット（`_attachSaveHandler()`, `desktop.js:1585-1627`）。
  2. iframe の URL が保存成功パターン（`/k/{appId}/show#record=N` かつ `mode=edit` を含まない）に遷移したことを、`load` イベント（`desktop.js:1818-1876`）と `hashchange` / 1500ms ポーリング（`_checkIframeUrl()`, `desktop.js:1901-1960`）の両方で検知する（`_isSaveSuccessUrl()`, `desktop.js:1644-1654`）。
  3. `_savePending && _isSaveSuccessUrl(loc)` が真になった時点（`desktop.js:1843-1855` および `:1911-1923`）で `_savePending` をリセットし、`KC.Render._refreshImmediate()` → `KC.Popup._close()` を呼ぶ。バリデーションエラー時は URL 遷移が起きないため、この分岐は通らない（コメント `desktop.js:1576-1578`）＝ **この分岐は必ず「保存成功後」**。
- **フック候補**: 上記 `desktop.js:1843-1855` と `:1911-1923`（load ハンドラ／ポーリングの2箇所、ロジックはほぼ重複しているため両方に同じフック呼び出しを追加する必要がある）。ここでは **レコード ID のみ**（URL の `record=N`）が分かり、フィールド値は分からない。ワークフロー実行のためには `KC.Api.getRecord(recordId)` での再取得が必須。
- 新規作成か編集保存かの区別: `openCreate` は `record=` パラメータなしで `/edit` を開始し、`openEdit` は `record=N` 付きで開始する。`KC.Popup` に現在「作成中か編集中か」を示すモード変数は存在しない（`_show(url)` は URL 文字列のみを受け取る）。ワークフローの「作成 / 更新」判定に必要なら、`_show()` 呼び出し元（`openCreate`/`openEdit`）で `KC.Popup._mode = 'create' | 'edit'` のような状態を追加保持する実装が必要（新規、既存コードに無い）。

#### 2.1.3 kintone 標準編集画面の保存（カレンダーを介さない）

- `kintone.events.on(['app.record.create.submit.success', 'app.record.edit.submit.success'], ...)`（`desktop.js:10832-10843`）が既に存在する。ただし現在の実装は `if (window.opener) { ... }` を分岐条件にしており、これは **旧アーキテクチャ（`window.open` によるポップアップ）を前提としたコード**（コメント `desktop.js:1463-1465` に明記の「旧実装: window.open による別ウィンドウポップアップ」に対応）。
- 現行の iframe オーバーレイモーダル方式では `window.opener` は常に `null`（iframe は `window.open` で開いていないため）。したがって **このハンドラのイベント自体は発火するが、`if (window.opener)` の中身は現状決して実行されない（事実上の死んだ分岐）**。
- 一方、`manifest.json`（`plugin/manifest.json:14-17`）は `desktop.js` をアプリの `desktop` カスタマイズとして登録しており、ビュー単位のスコープ指定はない。このため **同一の `desktop.js` が、カレンダービューだけでなく、このアプリの標準一覧・詳細・作成・編集画面（＝カレンダーの iframe モーダルが読み込む `/edit`・`/show` も含む）すべてに読み込まれる**。
- 結論: `app.record.create.submit.success` / `app.record.edit.submit.success` は、(a) カレンダーの iframe モーダル内で保存した場合と、(b) このアプリの通常の一覧・詳細画面から直接保存した場合の **両方で発火する**。(a) と (b) を区別せずにこのハンドラでワークフローを実行すると、カレンダー経由の保存が「トリガー1」と「トリガー3」の両方としてカウントされてしまう（§2.3・§3.5 NFR-1 参照）。

#### 2.1.4 削除

- `kintone.events.on('app.record.detail.delete.submit', ...)`（`desktop.js:10848-10855`）が既に存在し、同様に `if (window.opener)` ゲートのため現状は事実上死んだ分岐。
- `KC.Api.deleteEvent()`（`desktop.js:1431-1438`、DELETE `/k/v1/records.json`）は定義されているが、**呼び出し箇所がコードベース全体を検索しても存在しない（未使用/デッドコード）**。カレンダー UI 上に削除ボタン・削除操作の実装は見当たらず、削除は常にモーダル内の kintone 標準詳細画面（またはアプリの標準詳細画面）が持つ「削除」ボタン経由で行われている、と推定される。
- `KC.Popup` には保存ボタン検知（`_attachSaveHandler`）・キャンセルボタン検知（`_attachCancelHandler`）に相当する **削除ボタン検知の仕組みは存在しない**。削除後の画面遷移（一覧へのリダイレクト）は `_isAllowedUrl()`（`desktop.js:1674-1691`）の対象外 URL に該当するため、現状は「許可外 URL 遷移」として汎用的に `_close()` されるだけであり、「削除が成功したこと」を明示的に検知するロジックはない。
- `app.record.detail.delete.submit` は kintone JS API 上、削除確認ダイアログで「削除する」を押した際に発火する **削除実行前のキャンセル可能イベント**（`event.record` に削除対象レコードの全フィールド値が含まれる）である。`.submit.success` に相当する「削除確定後」イベントは、少なくとも本コードベースの既存実装ではハンドリングされていない（kintone 公式仕様上そのようなイベントが存在するか自体、本書では未確認。§7.1 U-3 参照）。

### 2.2 KC.Banner（既存の通知バナー）

- `KC.Banner`（`desktop.js:6968-7043`付近）は `.kc-root` 直下にシングルトンで挿入されるエラーバナー。`show(message, opts)` / `hide()` のみを持ち、**同時に表示できるメッセージは1件のみ**（`show()` 内、既存バナーがあればテキストを上書きするだけ。`desktop.js:6980-6986`）。
- 既存用途: DnD 重複チェック失敗時のブロック通知（`desktop.js:2313, 2318, 2336, 2343, 2345` 等）。
- ワークフロー失敗通知に流用する場合、DnD 重複チェックのバナーと表示が競合（後勝ちで上書き）する可能性がある（§7.2 R-2）。

### 2.3 対象アプリへのクロスアプリ REST 呼び出しの前例

- `KC.Api.checkOverlapQueryModeB()`（`desktop.js:1233-1388`、DnD重複チェック モードB）が、既に **自アプリ以外のアプリ（関連先アプリ）** へ `kintone.api(url, 'GET', { app: relatedAppId, ... })` を発行している（`desktop.js:1327-1332`）。
- 同関数は権限エラーを `err.code === 'CB_AU01' || err.status === 403` で判定し、`isPermissionError` フラグとして呼び出し元に返す実装（`desktop.js:1335-1337`）。この判定パターンはワークフローのエラーハンドリングでも流用できる（正確なエラーコード体系は §7.1 U-1 で確認事項として扱う）。
- `KC.Config.detectFields()`（`desktop.js:94-140`）・config.js の `loadFields()`（`config.js:2914-2919`）はいずれも自アプリの `app: KC.Config.getAppId()` / `app: getAppIdFromUrl()` で `/k/v1/app/form/fields.json` を呼んでいるが、**この API は `app` パラメータに任意のアプリ ID を指定すれば、そのアプリの閲覧権限を持つユーザーであれば取得可能**（kintone REST API 仕様上の一般則。本コードベースでは他アプリ ID を渡す実装はまだ存在しないため、これは新規実装が必要な箇所）。

### 2.4 config.js の設定保存形式（version 12 が現行 — 委譲時の前提と差異あり）

委譲プロンプトでは「config version 11」を前提としていたが、直近コミット `71d7d2a`（モードB filterCond 連動修正）で **既に version 12 に上がっている**ことをコード上で確認した（`config.js:3-23` のヘッダーコメント、`config.js:166`, `config.js:2745`, `config.js:2867`, `config.js:3526`）。本書ではこの事実を前提に、新機能導入時のバージョンを **version 13** として設計する。

- `currentConfig` のトップレベル構造（`config.js:160-191`）: `version, fieldMapping, permissionRules, fieldValueRules, searchTargets, defaultPermission, filterConfig, views`。
- `loadInitialConfig()`（`config.js:2724-2884`）が `version` を段階的に判定し、v2→v5→v6→v7→v8→v9→v10→v11→v12 の順で1段階ずつマイグレーションを適用する連鎖処理になっている（各 `if (Number(parsed.version) < N)` ブロック、`config.js:2764-2851`）。新規追加時も **この連鎖に1段追加するだけ**（既存マイグレーションを変更しない）で済む設計になっている。
- `saveConfig()`（`config.js:3376-3564`）内 `finalConfig`（`config.js:3525-3536`）が実際に `kintone.plugin.app.setConfig()` へ渡す最終オブジェクト。ここに新キーを追加する必要がある。

### 2.5 既存 UI パターン（新規 UI 設計の再利用対象）

- **行リスト（テーブル型・DnD 並び替え・追加/削除）パターン**: 権限フィールド設定（`buildFieldValueRow()`, `config.js:1434-1476`）・権限ユーザー設定（`buildPermissionRow()`, `config.js:1182`）・フィルタ設定（`buildFilterGroupRow()`, `config.js:2047`）が共通して採用。行ドラッグは `attachRowDragEvents(row, handle)`（`config.js:1087`）で共通化されており、`row.parentNode` を基準に `insertBefore` する実装のため、コンテナがどのセクションに置かれても機能する（`REQ_config-reorg.md §2.3` で確認済みの事実と同じ）。
- **「フィールド選択→値選択」連動パターン**: `buildFieldValueFieldSelect()`（`config.js:1508-1548`）でフィールド一覧セレクトを構築し、`buildFieldValueValueSelect()`（`config.js:1556-1573`）が `fieldSel` の `change` イベントで `rebuildValueSelect()` を呼び、選択フィールドの型に応じて値の選択肢（DROP_DOWN/RADIO_BUTTON の選択肢一覧、CHECK_BOX の複数選択等）を動的に再構築している。これはユーザーヒアリングで要望されている「発火条件（フィールド選択→値選択）」の実現方式として直接流用できる。
- **モーダルダイアログパターン**: `#kc-copy-modal`（`.kc-modal-overlay`、`config.html:509-527`、「ほかビューからの設定コピー」用）が既に存在する。設定画面全体はこの1箇所を除き単一ページのフラット構成（`REQ_config-reorg.md` で確認済みの5セクション構成、見出し行 `config.html:34, 147, 204, 316, 393`）だが、モーダル自体の実装パターンは既にあるため、ワークフローの「詳細編集」に転用可能（§3.7 参照）。

## 3. 要件

### 3.1 トリガー種別（FR-1）

| トリガー ID | 名称 | 発火元（実装フック） | 発火条件判定に使う値 |
|---|---|---|---|
| `calendarSave` | カレンダー: 作成・更新 | (a) DnD/リサイズ: `_commitOptimistic()` 内 `updateEvent().then()` 成功時（`desktop.js:2371-2378`）<br>(b) モーダル経由の保存: `KC.Popup` の保存成功検知（`desktop.js:1843-1855`, `:1911-1923`） | (a) は `KcEvent` 保持フィールド＋必要に応じ `getRecord()` 再取得<br>(b) は `getRecord(recordId)` で全フィールド取得（必須。§2.1.2） |
| `calendarDelete` | カレンダー: 削除 | `app.record.detail.delete.submit`（既存ハンドラ `desktop.js:10848-10855` を拡張。`window.opener` ゲートを撤去し新ロジックに置換） | `event.record`（イベント発火時点で削除対象レコードの全フィールド値を含む。削除確定前のスナップショットとして利用） |
| `kintoneEditSave` | kintone 編集画面: 保存 | `app.record.create.submit.success` / `app.record.edit.submit.success`（既存ハンドラ `desktop.js:10832-10843` を拡張） | `event.record`（保存後の全フィールド値を含む） |

**設計判断（重要）**: `kintoneEditSave` は「カレンダーを介さない、このアプリの標準編集画面での保存」に限定する。実装上、`desktop.js` は iframe 内にも読み込まれるため（§2.1.3）、**このハンドラが「カレンダー自身のモーダル iframe の中」で発火した場合は `kintoneEditSave` の対象外とし、何もしない**（トリガー1側 `calendarSave` の (b) が既にカバーするため、二重発火防止。§3.5 NFR-1 参照）。

判定方法（提案）: `KC.Popup._show()`（`desktop.js:1771`）で iframe 要素に識別用マーカーを付与する（例: `iframe.dataset.kcModal = '1'`）。iframe 内で実行される `desktop.js` の当該イベントハンドラは、`window.self !== window.top && window.frameElement && window.frameElement.dataset.kcModal === '1'` を満たす場合に「自分はカレンダーの iframe モーダルの中にいる」と判定し、`kintoneEditSave` の発火をスキップする。

### 3.2 ワークフロー定義の構成（FR-2）

ステップ列挙型・直列フローとして、1ワークフローを以下の階層で構成する。

```
ワークフロー
  ├─ 基本情報: 名前、有効/無効
  ├─ トリガー: トリガー種別（§3.1 の3種から1つ）
  ├─ 発火条件: 0件以上（AND結合。フィールド選択→値選択の行リスト）
  └─ アクション: 1件以上（上から順に実行するステップ列挙）
        ├─ 対象アプリ（アプリID）
        ├─ 動作モード: 新規作成のみ / 更新のみ / upsert（キー一致で検索し、あれば更新・なければ新規作成）
        ├─ キー一致設定（更新のみ・upsert 時に必須）: 自アプリのフィールド ⇔ 対象アプリのフィールド
        ├─ 複数件ヒット時の扱い: 更新をブロックしエラー扱い（既定・固定。§3.4.4）
        ├─ フィールドマッピング: 対象アプリの各フィールドに対し「自アプリのフィールド値」または「固定値」を割り当て
        └─ このアクションが失敗した場合、後続アクションを実行するか（既定値の提案は §3.4.6。要ユーザー確認）
```

1つのトリガー種別に対して複数のワークフローを定義できる（例: `calendarSave` に対して2つの独立したワークフローを設定可能）。ワークフロー間の実行順序は「ワークフロー一覧」内の並び順（DnD 並び替え）に従う。

### 3.3 発火条件（FR-3）

- 0件（無条件で常に実行）〜複数件（AND結合のみ。OR結合は将来拡張）。
- UI は §2.5 の「フィールド選択→値選択」パターン（`buildFieldValueFieldSelect`/`buildFieldValueValueSelect`, `config.js:1508-1573`）を流用する。
- 対象フィールドの型は、既存の権限フィールド設定と同様に DROP_DOWN / RADIO_BUTTON / CHECK_BOX / STATUS を基本としつつ、ワークフローでは加えて **SINGLE_LINE_TEXT 等の文字列系フィールドとの完全一致条件** も必要になる可能性が高い（例:「特定の申請番号の時だけ実行」）。対象フィールド型の最終確定は §7.1 U-2 で確認する。
- 判定に使う値の取得元は、トリガー種別ごとに §3.1 の表の「発火条件判定に使う値」列に従う（`calendarSave` の DnD 経路のみ、KcEvent に値が無い場合は追加 GET が必要になる点に注意。§2.1.1）。

### 3.4 アクション（FR-4）

#### 3.4.1 対象アプリ・フィールド取得

- 設定画面でアプリ ID を入力すると、`/k/v1/app/form/fields.json`（`app: <入力されたID>`）を呼び出しフィールド一覧を取得する（§2.3 で確認した通り、他アプリ ID を渡しても閲覧権限があれば取得可能）。
- 取得失敗時（アプリが存在しない／権限がない）はエラーメッセージを表示し、フィールドマッピング UI を無効化する。

#### 3.4.2 動作モード

| モード | 挙動 |
|---|---|
| 新規作成のみ | 常に `POST /k/v1/record.json`（`app: targetAppId`）でレコードを追加する |
| 更新のみ | キー一致検索でヒットしたレコードのみ `PUT /k/v1/record.json` で更新する。ヒットしない場合は「何もしない」（エラー扱いにはしない） |
| upsert | キー一致検索を行い、ヒットすれば更新、ヒットしなければ新規作成する |

#### 3.4.3 フィールドマッピング

- 対象アプリの各フィールドに対し、(a) 自アプリのフィールド値をそのまま渡す、(b) 固定値を設定する、のいずれかを選択できる。
- 型不一致の扱い（提案。§7.1 U-4 で最終確認）:
  - DATETIME → DATE: 日付部分のみを渡す（`createEvent`/`updateEvent` の DATE 変換ロジック `desktop.js:1082-1090, 1396-1404` と同様、時刻を切り捨てる）。
  - DATE → DATETIME: 00:00:00 を補完して渡す。
  - USER_SELECT → SINGLE_LINE_TEXT 等: ユーザー名（`name`）またはコード（`code`）のどちらを渡すか設定可能にする（既定はコード）。
  - CHECK_BOX（複数選択）→ 単一値系フィールド: 非対応（設定画面でこの組み合わせの選択自体を禁止する）。
  - それ以外の未対応の組み合わせは、設定保存時のバリデーションでブロックし、エラーメッセージを表示する。
- DnD トリガー（`calendarSave` の (a)）でマッピング元フィールドが `KcEvent` に保持されていない場合、ワークフロー実行時に `KC.Api.getRecord(ev.id)` で該当レコードを再取得してから mapping を評価する（§2.1.1）。

#### 3.4.4 キー重複・複数ヒット時の挙動

- キー一致検索で対象アプリ側に **2件以上ヒットした場合は、更新を行わずエラー扱い**とする（安全側デフォルト。どのレコードを更新すべきか自動判断しない）。
- バナー通知例:「ワークフロー『{name}』: キー『{自アプリフィールド}={値}』に一致するレコードが対象アプリ側に複数件見つかったため、更新をスキップしました。」

#### 3.4.5 実行順序

- アクションは配列順に**逐次実行**する（並列実行はしない。前段の結果を後段が使うケースを将来的に許容するため）。

#### 3.4.6 失敗時の継続/中断（要ユーザー確認）

- 提案: 既定値は「継続」（`continueOnError: true`）。ベストエフォート方針（§3.6 NFR-3）と整合させ、1つのアクションの失敗が後続アクション・カレンダー本体の保存を止めないことを既定とする。
- アクションごとに「失敗時に後続を中断する」チェックボックスで上書き可能にする（既定 OFF＝継続）。
- **この既定値（継続 vs 中断）はヒアリング未確定。§7.1 U-5 で確認する。**

### 3.5 二重発火防止（NFR-1）

- `calendarSave` と `kintoneEditSave` は、同一の保存操作に対して片方のみが発火するよう、§3.1 の iframe マーカー判定で排他制御する。
- `calendarSave` 内部（DnD 経路 と モーダル経路）は、それぞれ独立した操作（DnD操作 or モーダルでの保存操作）に対応するため、同一操作が両方から二重発火することは構造上ない。
- モーダル経由の保存検知（`_isSaveSuccessUrl` 判定、`desktop.js:1843-1855` の load ハンドラと `:1911-1923` のポーリング/hashchange ハンドラ）は、`_savePending` フラグを検知直後にリセットする実装（`desktop.js:1845, 1913`）のため、単一実行環境（JS シングルスレッド）において2つの検知経路が同一の保存を二重処理することはない（既存コードで担保済み。ワークフロー呼び出しをこのブロックの中に追加するだけでよい）。
- ワークフロー間の多重実行（同一トリガーに複数ワークフローを設定した場合の意図した複数実行）は二重発火とは区別する（仕様通りの動作）。
- **スコープ外の残存リスク**: 複数アプリにまたがるワークフローの循環（例: A アプリのワークフローが B アプリを更新し、B アプリ側にも本プラグインが導入されていて B → A へ書き戻すワークフローが設定されている場合の無限ループ）は、本プラグインが単一アプリの config のみを管理する設計上、**技術的な自動検知はスコープ外**とし、運用上の注意事項として明記する（§7.2 R-1）。

### 3.6 実行方式・パフォーマンス（NFR-2）

- ワークフロー実行は**非同期・fire-and-forget**とする。カレンダー本体の保存・削除・モーダルクローズ・再描画を待たせない。
  - DnD: `updateEvent(payload).then(function (resp) { ...; KC.Workflow.run(...).catch(...); })` のように、既存の非ブロッキング `.then` チェーンの中で呼び出す（`await` しない）。
  - モーダル保存検知: `KC.Render._refreshImmediate()` / `KC.Popup._close()` の呼び出し（`desktop.js:1850-1853`, `:1918-1921`）をブロックしない位置で `KC.Api.getRecord()` → ワークフロー実行を非同期に開始する。
  - `kintoneEditSave` / `calendarDelete`: kintone イベントハンドラは `return event` を同期的に即座に行い、ワークフロー実行はその前後で `await` せず非同期に開始する（`kintone-rules.md` の「event は必ず return する」を遵守しつつ、ワークフロー完了を待たない）。
- 複数アクションは逐次実行だが、各アクションの REST 呼び出し自体は非同期（Promise chain）。UI 側のローディング表示・ブロッキングは行わない。

### 3.7 エラーハンドリング・通知（NFR-3）

- 方針: **ベストエフォート**。カレンダー側の操作（作成・更新・削除）自体は、ワークフローの成否に関わらず既に完了しているため、ロールバックはしない。
- 失敗時（権限不足・対象アプリ削除・キー重複複数ヒット・ネットワークエラー等）は、`KC.Banner`（`desktop.js:6968-7043`）を用いてカレンダー画面上部に通知する。
  - 既存の DnD 重複チェックバナーと同時に表示され得る点は制約として残る（§7.2 R-2 で対応方針を確認）。
  - 権限エラー判定は `checkOverlapQueryModeB()` の前例（`err.code === 'CB_AU01' || err.status === 403`, `desktop.js:1335-1337`）を踏襲するが、対象アプリへの「レコード追加・更新権限不足」で実際に返るエラーコードは異なる可能性がある（§7.1 U-1）。
  - `console.error` にも詳細（ワークフロー名・アクション・対象アプリID・エラー内容）を出力する。
- 成功時は特に通知しない（サイレント成功。ログのみ `console.log`／`_log`）。

### 3.8 削除トリガーのスナップショット（NFR-4）

- `app.record.detail.delete.submit` は削除実行前に発火し `event.record` に削除対象レコードの全フィールド値を含む（§2.1.4）。この `event.record` をそのままワークフローの発火条件判定・フィールドマッピングのソースとして使用する。
- 追加の GET は不要（削除後は当該レコードが存在しなくなるため GET できない。イベント時点のスナップショットを使うことが必須）。
- **リスク**: このイベントは「削除確定前」に発火するため、何らかの理由でこの後の実際の DELETE 処理自体が失敗した場合（サーバー側エラー・権限不足等）でも、ワークフロー側は既に実行されてしまう可能性がある（§7.2 R-3）。

## 4. 受入基準

Given/When/Then 形式で記述する。

### AC-1: カレンダー経由の作成・更新（モーダル）がワークフローの `calendarSave` トリガーを発火する

- **Given** `calendarSave` トリガーのワークフローが1件、条件なしで有効化されている
- **When** 管理者がカレンダーの新規作成モーダルで予定を作成し保存する
- **Then** 保存成功検知（`_isSaveSuccessUrl` 判定）の直後に、当該ワークフローのアクションが実行される
- **And** カレンダーのモーダルクローズ・再描画はワークフローの完了を待たずに行われる

### AC-2: DnD（移動・リサイズ）が `calendarSave` トリガーを発火する

- **Given** `calendarSave` トリガーのワークフローが1件、有効化されている
- **When** 管理者がカレンダー上で予定をドラッグ&ドロップして移動し、重複チェック（有効時）を通過して PUT が成功する
- **Then** PUT 成功コールバック内でワークフローのアクションが実行される
- **And** DnD 操作自体の UI 応答（ゴースト解除・再描画）はワークフロー完了を待たない

### AC-3: kintone 標準編集画面からの直接保存が `kintoneEditSave` トリガーを発火し、カレンダーモーダル経由の保存では発火しない

- **Given** `kintoneEditSave` トリガーのワークフローが1件、有効化されている
- **When** (a) このアプリの通常の一覧画面から直接レコードを編集・保存する
- **Then** (a) の場合はワークフローが実行される
- **When** (b) カレンダーの編集モーダル（iframe）経由でレコードを保存する
- **Then** (b) の場合は `kintoneEditSave` トリガーのワークフローは実行されない（`calendarSave` 側のみ実行される）

### AC-4: 削除トリガーが削除前のフィールド値でワークフローを実行する

- **Given** `calendarDelete` トリガーのワークフローが1件、削除対象レコードのあるフィールド値を条件に指定して有効化されている
- **When** 管理者がカレンダーのモーダル内、または標準画面からレコードを削除する
- **Then** `app.record.detail.delete.submit` イベントの `event.record` を用いて条件判定・フィールドマッピングが行われ、対象アプリへのアクションが実行される

### AC-5: upsert モードでキー一致検索を行い、既存レコードがあれば更新、なければ新規作成する

- **Given** upsert モードのアクションが設定されたワークフロー
- **When** キー一致検索で対象アプリに1件ヒットする
- **Then** そのレコードが PUT で更新される
- **When** キー一致検索で対象アプリに0件ヒットする
- **Then** POST で新規レコードが作成される

### AC-6: キー一致検索で複数件ヒットした場合は更新をブロックしエラー通知する

- **Given** upsert または更新のみモードのアクション
- **When** キー一致検索が対象アプリで2件以上ヒットする
- **Then** 更新は行われず、`KC.Banner` にエラーメッセージが表示され、`console.error` にも記録される

### AC-7: 対象アプリへの権限不足時、カレンダー側の操作自体は成功として完了する

- **Given** ログインユーザーが対象アプリへの追加・更新権限を持たない
- **When** カレンダーで予定を作成・保存する（`calendarSave` トリガー発火）
- **Then** カレンダー側の予定作成自体は成功し、モーダルは正常に閉じる
- **And** ワークフローのアクション実行は失敗し、`KC.Banner` にエラーメッセージが表示される

### AC-8: 発火条件に一致しない場合はワークフローが実行されない

- **Given** 発火条件（フィールド=値）が設定されたワークフロー
- **When** 条件に一致しないレコードで `calendarSave` トリガーが発火する
- **Then** ワークフローのアクションは一切実行されない

### AC-9: 型不一致の未対応な組み合わせは設定保存時にブロックされる

- **Given** フィールドマッピングで CHECK_BOX（複数選択）を単一値系フィールドへマッピングしようとする
- **When** 設定画面で「保存」を実行する
- **Then** バリデーションエラーが表示され保存されない

### AC-10: config のマイグレーション（v12→v13）が既存データを保持する

- **Given** version 12 形式で保存済みの既存 config データを持つアプリ
- **When** 再編後のプラグイン設定画面を開く
- **Then** `workflows: []` が補完され、既存の他のキー（`fieldMapping` 等）は変更なく復元される

### AC-11: ワークフロー一覧・詳細編集モーダルの2階層 UI が機能する

- **Given** セクション6「ワークフロー」を開く
- **When** 「+ ワークフローを追加」を押し、詳細編集モーダルでトリガー・条件・アクションを設定して「適用」を押す
- **Then** モーダルが閉じ、ワークフロー一覧に新しい行が追加される
- **And** 画面下部の「保存」を実行すると `workflows` 配列が `setConfig` で永続化される

## 6. 想定 UX / シーケンス

### 6.1 カレンダー: 作成・更新（モーダル経由）

```
管理者がカレンダーの「+予定を追加」→ 新規作成モーダル（iframe）表示
  → kintone標準の保存ボタンをクリック（KC.Popup._attachSaveHandler が _savePending=true）
  → 保存API成功 → iframe が /show#record=N へ遷移
  → KC.Popup が _isSaveSuccessUrl を検知（load / hashchange / polling のいずれか）
     → KC.SearchFilter._invalidateRelatedRecordsCache()
     → KC.Render._refreshImmediate()
     → KC.Popup._close()（モーダルを閉じる。ここまでは既存動作、変更なし）
     → （非同期・並行）KC.Workflow.run('calendarSave', recordId)
        → KC.Api.getRecord(recordId) でレコード全体を取得
        → 該当する有効なワークフローを config.workflows から抽出
        → 各ワークフローの発火条件を判定 → 一致するものだけアクションを実行
        → アクション: 対象アプリのフィールド取得済み情報を使いレコード組み立て
           → matchKey でキー一致検索 → upsert/createOnly/updateOnly に応じ POST/PUT
        → 失敗時は KC.Banner.show(...) で通知
```

### 6.2 カレンダー: DnD（移動・リサイズ）

```
管理者が予定バーをドラッグ→ドロップ
  → 楽観的UI更新（即時反映）
  → 重複チェック（有効時）→ 重複なければ次へ
  → KC.Api.updateEvent(payload)（PUT, revision付き）
     .then(resp) 成功
        → currentEv.rev 更新（既存動作）
        → （非同期・並行）KC.Workflow.run('calendarSave', { ev: origEv, updated: payload })
           → 必要なマッピング元フィールドが KcEvent に無ければ KC.Api.getRecord(ev.id) で補完
           → 以降 §6.1 と同様
     .catch(err) 失敗 → alert + ロールバック（既存動作、変更なし。ワークフローは実行しない）
```

### 6.3 kintone 編集画面: 保存（カレンダーを介さない）

```
ユーザーがこのアプリの通常の一覧・詳細画面からレコードを編集し保存
  → app.record.edit.submit.success 発火
  → ハンドラ内で「自分は kc-modal iframe の中か？」を判定
     → iframe の中（= カレンダーモーダル経由）→ 何もしない（calendarSave 側が別途処理済み）
     → iframe の外（= 通常の kintone 画面）→ KC.Workflow.run('kintoneEditSave', event.record)
  → return event（同期・即座。ワークフロー完了を待たない）
```

### 6.4 カレンダー: 削除

```
ユーザーが削除対象レコードの詳細画面（カレンダーモーダル内 or 標準画面）で「削除」→確認
  → app.record.detail.delete.submit 発火（削除実行前・event.record にスナップショットあり）
  → KC.Workflow.run('calendarDelete', event.record) を非同期起動（await しない）
  → return event（削除処理を継続させる）
  → （非同期）ワークフロー実行 → 失敗時は次回カレンダー描画時にバナー表示
     （削除操作自体の画面には既にワークフロー結果を表示する手段がないため、
       カレンダー本体側の再読み込み時にバナーが出る形になる点に注意。§7.1 U-6）
```

### 6.5 設定画面: ワークフローの新規作成

```
管理者が設定画面「ワークフロー」セクションを開く
  → 「+ ワークフローを追加」→ 詳細編集モーダル表示
  → 名前・トリガー種別を選択
  → 発火条件を0件以上追加（フィールド選択→値選択）
  → アクションを1件以上追加
     → 対象アプリID入力 → 「フィールド取得」→ フィールド一覧セレクトが有効化
     → 動作モード選択（新規作成のみ/更新のみ/upsert）
     → upsert・更新のみの場合はキー一致設定（自アプリ⇔対象アプリのフィールド）
     → フィールドマッピング行を追加（対象アプリフィールド ← 自アプリフィールド or 固定値）
  → 「適用」→ モーダルを閉じ、ワークフロー一覧に反映（メモリ内 currentConfig.workflows 更新）
  → 画面下部「保存」または「保存して更新」→ setConfig で永続化（version 13）
```

## 8. 改訂1: トリガー再編（2026-07-15 ユーザー指示・確定）

初回実装完了後のユーザーレビューにより、トリガーの切り口を「経路別」から「操作別」に変更する。**§3.1 の3トリガー（calendarSave / calendarDelete / kintoneEditSave）は本節の定義で置き換える。**

### 8.1 新トリガー種別（操作別・経路は区別しない）

| トリガー ID | 名称 | 発火元（全経路を統合） |
|---|---|---|
| `recordCreate` | レコード作成時 | (a) カレンダー新規作成モーダルの保存成功（`KC.Popup._mode === 'create'`）、(b) `app.record.create.submit.success`（iframe 外＝標準画面） |
| `recordUpdate` | レコード更新時 | (a) DnD/リサイズの PUT 成功、(b) カレンダー編集モーダルの保存成功（`KC.Popup._mode === 'edit'`）、(c) `app.record.edit.submit.success`（iframe 外） |
| `recordDelete` | レコード削除時（物理削除） | `app.record.detail.delete.submit`（従来の `calendarDelete` と同一。削除前スナップショット利用） |

- 「カレンダー DnD か kintone 編集画面か」という**経路の区別は行わない**（ユーザー確定）。
- 二重発火防止（§3.5 の iframe マーカー）は従来通り: モーダル経由の保存は親ウィンドウ側の (a)/(b) のみが発火し、iframe 内の kintone イベントはスキップする。

### 8.2 論理削除の扱い（ユーザー確定）

- 運用上の「削除」はフィールドによる論理削除（例: ステータス=削除済）であるため、専用トリガーは設けず **`recordUpdate` ＋ 発火条件** で表現する。
- 発火セマンティクスは**状態一致・毎回発火**（削除済み状態のレコードが保存されるたびに発火する。「削除済みになった瞬間のみ」の遷移検知は行わない）。アクションが upsert であれば再発火は実害がない、という前提をユーザーと確認済み。
- 設定画面のトリガー選択部のヘルプ文に「論理削除（ステータス等での削除フラグ）を扱う場合は『レコード更新時』＋発火条件で設定する」旨を明記する。
- 遷移検知（〜になったときのみ発火）は将来拡張とし本書のスコープ外。

### 8.3 実装への影響

- **`KC.Popup._mode` の新設が必要になる**（§7.1 U-8 の再確定。初回実装では「calendarSave が作成/更新を区別しないため不要」と判断し省略したが、本改訂で区別が必要になった）。`openCreate()` で `'create'`、`openEdit()` で `'edit'` をセットし、保存成功検知時に参照する。
- config の `trigger.type` は新 enum（`recordCreate` / `recordUpdate` / `recordDelete`）に変更する。**version 13 は未リリース（未コミット）のため、旧 enum からのマイグレーションは不要**。version 番号も 13 のまま。
- 設定画面のトリガーセレクトは「レコード作成時／レコード更新時／レコード削除時（物理削除）」の3択に変更。
- `KC.Workflow.Core` への影響なし（トリガー分類は Core の外＝トリガー側の責務）。

### 8.4 受入基準（追加・AC-1〜AC-3 を置き換え）

- **AC-12**: 新規作成（モーダル or 標準画面）では `recordCreate` のみ発火し、`recordUpdate` は発火しない
- **AC-13**: 更新（DnD・編集モーダル・標準画面編集のいずれも）では `recordUpdate` のみ発火し、`recordCreate` は発火しない。経路によらず同一ワークフローが発火する
- **AC-14**: 「`recordUpdate` ＋ 条件: 削除フラグ=ON」のワークフローは、論理削除操作（フラグを ON にして保存）で発火し、フラグ OFF のレコードの通常更新では発火しない
